## Journey Overview

Catalogue #159 covers disconnection of an MSISDN (mobile number) across Prepaid, Postpaid, Fiber, and FWA lines, including the special case of "star numbers" (premium/high-value numbers), executed today as a Trouble-Ticket-gated Order on the Open UI/Siebel "Vanilla" desktop front end. Per the workshop [00:55:12], disconnection is **not** a direct order-entry action — it is deliberately routed through the Trouble Ticket (TT) system first, specifically so that a retention team, not the requesting agent, makes the actual disconnect/retain decision. Only once the ticket is closed with the correct resolution code does the Orders page unlock the ability to submit a disconnection order.

Two categories of business rule stack on top of the base disconnection ticket flow:
1. A **retention-first gate**: any agent can raise a disconnection ticket, but only the retention team can close it, and only a specific resolution code on that closure unlocks the disconnection order [00:55:16, 00:57:00, 00:57:53].
2. **Penalty checks**: plan/commitment penalties are calculated automatically; star-number and device penalties are not — they are checked manually by the retention agent today, with automation of those two penalty types called out as a separate, not-yet-delivered project [00:57:56, 00:59:00, 00:59:07].

## Workflow Steps

1. **Trigger — customer requests disconnection.** Customer contacts Vodafone (call or store visit) requesting disconnection of an MSISDN (any of Prepaid/Postpaid/Fiber/FWA). [Consistent with the general ticket-creation trigger pattern documented at 00:03:48; disconnection is explicitly listed as one of the Request-ticket sub-types at 00:02:37.]
2. **Frontline agent creates a Disconnection request ticket** using the standard BAU ticket-creation flow: open the customer account → Trouble Ticket section → "+" icon → ticket ID auto-generated → agent fills source, TT category ("Disconnection"), area, sub-area, language, description (using the Knowledge Base description template) → submits. [00:04:30, 00:05:08, 00:05:21, 00:55:12 — "Disconnection ticket created as BAU like normal tickets, but with one extra layer..."]
3. **Ticket routes to the Retention team queue.** TT category/area/sub-area combination determines routing; a retention-type request routes specifically to the Retention team (~50+ agents per the team-size answer at [00:11:24], which also states Retention handles migration and disconnection queues). [00:07:45, 00:26:12]
4. **Retention agent contacts the customer to attempt to retain them.** This is explicitly a "retention ticket" — the act of raising a disconnection TT triggers a retention conversation, not an immediate disconnect. [00:56:02 — "When a disconnection ticket is raised the retention team contacts the customer; it is a retention ticket."]
5. **Retention agent manually checks termination/commitment penalties before proceeding.** Confirmed twice: as an assumption ("Termination penalties are checked by the agent before proceeding to disconnect," [00:55:55]) and directly in Q&A ("For disconnection do you ask for any attachment? No... the agent checks termination penalties before proceeding to disconnect," [00:55:44]). Only plan/long-term-commitment penalties are system-automated at this point; star-number and device penalties must be manually checked by the retention agent as a separate business-rule step [00:57:56, 00:59:00].
6. **Decision — is the customer retained?**
   - **If retained:** the retention agent closes the ticket with the resolution code that signals "retained." [00:56:02, 00:57:00] No disconnection order is created; the MSISDN remains active. Journey ends here.
   - **If not retained:** retention itself (not the original requesting agent) takes the decision to proceed with disconnection — "Not every agent can disconnect; a rule was created that the customer must be offered retention first" [00:57:53]; "If the customer is not retained, who takes the action? The retention team themselves take the decision. Previously any agent could disconnect; a rule was created so retention is offered first" [00:56:54].
7. **Retention agent closes the ticket with the "not retained" resolution code.** This is the literal unlock condition: "Closing a disconnection ticket with a specific resolution code allows the disconnection order to be created and submitted" [00:55:16]. Before Siebel/Open UI enforced this gate, ticket closure and order submission were not linked in this controlled way (implied by the rule being described as deliberately "created").
8. **System/agent applies automated plan/commitment penalty calculation** as part of finalizing the disconnect path (only this penalty type is automated today) [00:57:56].
9. **Decision — is a star number or device installment involved?**
   - **If yes:** retention agent manually determines and applies the star-number penalty and/or device (installment) penalty — no system automation exists for these two penalty types yet; a separate project is underway to automate them [00:57:56, 00:59:00, 00:59:07]. A known gap: the star-number penalty today is recorded as a "floating adjustment" that cannot be linked back to the originating request/order — flagged as an improvement opportunity, not yet fixed [01:03:56].
   - **If no:** skip to step 10 with only the automated plan penalty applied.
10. **Agent (retention) navigates to the Orders page**, selects "Disconnection" as the order type, and submits the disconnection order against the MSISDN. [00:55:12, 00:04:30-style Orders-page pattern]
11. **Disconnection order is submitted/processed**, and the MSISDN moves to disconnected status. (The transcript does not describe the order-fulfillment back-end steps after submission — e.g., provisioning system calls, billing account closure — only that the order is "submitted" from the Orders page; this is a known gap, see Data Inputs/Outputs below.)

- **Retained customers:** ticket closes with a different resolution code; no order created (see D1 "Yes" branch).
- **Unautomated penalty types (star number, device):** handled as a manual exception process by the retention agent today; explicitly slated for future automation in a separate project [00:59:07]. ## Business Rules

1. **Retention-first gate (primary rule for this journey).** "Not every agent can disconnect; a rule was created that the customer must be offered retention first" [00:57:53]. Mechanically enforced via ticket-resolution-code-to-order-unlock: "Closing a disconnection ticket with a specific resolution code allows the disconnection order to be created and submitted" [00:55:16]. The retention team, not the originating agent, makes the final retain/disconnect call: "If the customer is not retained, who takes the action? The retention team themselves take the decision. Previously any agent could disconnect; a rule was created so retention is offered first" [00:56:54].
2. **Star-number and device penalty rule.** "Only plan penalties are automated; star number and device penalties are business rules the retention agent must check manually" [00:59:00]. Automation of these two penalty types is planned as a separate initiative, not yet delivered: "Star number penalties and device penalties are being automated in a separate project" [00:59:07].
3. **Star-number penalty linkage gap.** The star-number penalty today is applied as "a floating adjustment which cannot be linked against the port-out request" — flagged as a risk/improvement item, not a fix already made [01:03:56]. (Framed around port-out in the source table, but the same manual/unlinked-penalty pattern applies to disconnection per [00:57:56]/[00:59:00].)
4. **Commitment-period / regulatory rule (adjacent to, not exclusive to, disconnection).** "If the customer disconnects/terminates before the commitment period, a penalty must be paid" [01:01:18] — this is the one explicit statement tying a commitment-period penalty directly to termination/disconnection. The broader regulatory dispute (plan-change commitment continuation on upgrade vs. breach on downgrade) is a related open compliance issue flagged for a dedicated future session, not a fully resolved disconnection-order rule today [01:00:47, 01:00:52, 01:01:41].
5. **No attachment required** for a disconnection ticket [00:55:44].
6. **Ticket-vs-order modeling debate (open, unresolved):** "Disconnection could be modelled as an order rather than a ticket, but retention wants to keep ticketing because that is how they track" [00:57:07] — recorded as an assumption/open design question, meaning the current ticket-gated design is a deliberate choice by the retention team, expected to be revisited.
