## Journey Overview

Catalogue #110 governs an agent (VFQA Sales / back-office responsibility) changing the Bill
Limit (a.k.a. "Spend Limit") on an existing customer's postpaid MSISDN, via a **Modification
Order** raised against the installed Mobile Service Bundle asset (per the catalogue Description).
Bill Limit is a spend-cap product (e.g. "Bill Limit Mobile" or "Bill Limit Mobile Plus") mapped
in Product Administration with three governing values: **Agent Min Value** (floor an agent may
set without escalation), **SL Min Value** (absolute floor, e.g. 0.01), and **SL Default Value**
(e.g. 20). The value an agent enters is separately capped by the account's **Credit Limit**. Both
directions of the request are in scope: raising or lowering the Bill Limit.

This exact validation chain (Bill Limit vs. Agent Minimum, Bill Limit vs. Credit Limit) is
directly evidenced firing during two *other* order types (new Postpaid Sales Order — source #3;
Prepaid→Postpaid Plan Change/Upgrade Promotion order — source #4), and the catalogue confirms
#110's real-world execution path is the same rule set, but invoked from a Modification order
against an existing line.

## Workflow Steps (numbered)

1. **Trigger.** Agent (VFQA Sales / CSR) determines a customer's Bill Limit needs to change
   (increase or decrease) on an existing postpaid MSISDN. [Catalogue Description, source #1/#2]
2. **Locate account/asset.** Agent opens the customer's Account/Asset record and locates the
   Mobile Service Bundle installed asset for the target MSISDN. **[INFERRED]** by analogy to the
   asset-context-menu pattern actually observed in source #4 (right-click on an installed asset →
   Suspend / Modify / Disconnect / Upgrade Promotion / etc.), since #110 is asset-anchored
   ("against MSISDN") per its catalogue description.
3. **Raise a Modification Order.** Agent invokes the Modify action against the asset, which
   creates a Modification-type order (as opposed to the Sales Order / Plan Change order types
   seen in sources #3/#4). [Catalogue Description, source #1/#2 — "through Modification Order"]
4. **Open Bill Limit product configuration.** Within the order's line-item configurator, the
   agent opens the Bill Limit product's "Customize"/detail panel — directly observed UI pattern:
   a Bill Limit radio group (None / Bill Limit Mobile / Bill Limit Mobile Plus) with a gear/
   "Customize" icon opening a "Spend Limit Amounts" tab. [source #3, step 7–8; source #4, step 9]
5. **Enter new Bill Limit (SL Limit Amount).** Agent types the new value into "SL Limit Amount"
   (observed fields alongside it: SL Min Value, SL Default Value). [source #3 step 8; source #4
   step 10]
6. **Client-side informational note on Validate.** When the agent triggers order Validate, the
   system first surfaces a non-blocking informational dialog: *"Note: Maximum Bill Limit is
   equivalent to account Credit Limit. Please communicate this to customer."* — dismissed with
   OK, does not block. [source #3 step 11; source #4 step 12, verbatim in both]
7. **Rule evaluation (decision branching — see Decision Points below).** The order-validation
   workflow evaluates the entered Bill Limit against, in turn: blank/format checks (BL RULE 08,
   09), Agent Minimum (observed as Siebel error SBL-EXL-00151 in both sources, corresponding in
   spirit to BL RULE 04/05), Credit Limit ceiling (BL RULE 07), and in-flight/conflicting-order
   checks (BL RULE 01–03).
8. **Blocking error path.** If any rule fails, Validate returns a blocking dialog naming the
   specific violation (e.g. *"Bill Limit can not be set lower than Agent Minimum 80. Please
   Contact the System Administrator with Reference # 1-DAFQWTQ.(SBL-EXL-00151)"* — source #3 step
   12; *"...Reference # 1-D982OQU.(SBL-EXL-00151)"* — source #4 step 13). The order remains in
   **Pending** status; agent must correct the value and re-validate, or escalate to System
   Administrator. Neither source shows a captured retry/correction screenshot — **[GAP: no
   screenshot of a corrected resubmission]**.
9. **Success path.** If all BL RULE checks pass, order Validate proceeds without a blocking
   dialog (source #4 step 10 shows an intermediate "Check Errors generated (0) errors" state for
   a passing Bill Limit value of 55 against an Agent Minimum of 80 — note this is *before* the
   order-level Validate call, which in that same walkthrough subsequently *does* fail once the
   full order-level check runs, showing "Check Errors" and order-level "Validate" are distinct
   gates and a value can pass the former yet fail the latter).
10. **Submit / order completion.** **[INFERRED]** Agent submits the Modification order once
    Validate passes; per catalogue and general Siebel order lifecycle pattern observed elsewhere
    in this corpus, the order would move from Pending toward Complete (asynchronously, possibly
    via backend order orchestration). No source screenshot shows a completed #110 Modification
    order specifically.
11. **Persisted result.** The new Bill Limit value is attached to the Mobile Service Bundle /
    Bill Limit line item on the asset for that MSISDN going forward (by analogy to how the
    Credit Limit edit in source #5 was shown to persist back onto the Account record after order
    creation).

## Decision Points

1. **Is Bill Limit value blank?** → If blank: reject, **BL RULE 08** — "Bill Limit Cannot be left
   blank." (`ORD_VALD_RULE_168`)
2. **Is Bill Limit a valid non-negative number?** → If not (e.g. non-numeric or negative): reject,
   **BL RULE 09** — "You have entered an incorrect Limit Amount! Please ensure to only enter a
   number greater than or equal to 0!" (`ORD_VALD_RULE_169`)
3. **Is Bill Limit ≥ Agent Minimum Value** (the value configured per Bill Limit product in
   Product Administration, e.g. 80 for Bill Limit Mobile Plus in both sources)? → If lower:
   reject. Directly observed user-facing text (both sources, identical): *"Bill Limit can not be
   set lower than Agent Minimum [N] Please Contact the System Administrator with Reference #
   [ref].(SBL-EXL-00151)"*. This maps conceptually to **BL RULE 04** ("Cannot Proceed! Please
   Update Bill Limit to a higher value.", `ORD_VALD_RULE_165`) and/or **BL RULE 05** ("Bill Limit
   cannot be set lower than configured minimum amount. Please set to above configured minimum
   value or choose the other Bill Limit product.", `ORD_VALD_RULE_166`) — the corpus does not
   give a 1:1 mapping from the SBL-EXL-00151 UI text to a single BL RULE #, so both are cited as
   the closest documented match.
4. **Is Bill Limit ≤ account Credit Limit?** → If higher: reject, **BL RULE 07** — "Bill Limit
   Value cannot be more than Credit Limit!" (`ORD_VALD_RULE_167`). Reinforced by the
   non-blocking advisory shown at Validate time in both sources: "Maximum Bill Limit is
   equivalent to account Credit Limit."
5. **Does an in-flight (open/pending) order already exist that adds/updates Bill Limit on this
   account?** → If yes: reject, **BL RULE 02** — "Inflight order Adding/Updating Bill Limit
   found. Cannot Proceed!" (`ORD_VALD_RULE_163`)
6. **Does an in-flight order exist adding a Paid Add-on?** → If yes: reject, **BL RULE 03** —
   "Inflight Order adding Paid Addon found. Cannot Proceed!" (`ORD_VALD_RULE_164`)
7. **Do Paid Add-Ons exist in the *current* order alongside a Bill Limit modification?** → If
   yes: reject, **BL RULE 01** — "Bill Limit Modification to be done in a separate order as Paid
   Add-Ons are present in this Order!" (`ORD_VALD_RULE_162`) — i.e. Bill Limit changes must be
   isolated to their own order when Paid Add-Ons are involved.
8. **All checks pass** → Validate succeeds, order proceeds toward submission/completion.

## Exception Handling

- **SBL-EXL-00151 (Siebel business-rule exception, blocking).** Directly observed verbatim twice
  (source #3 ref 1-DAFQWTQ; source #4 ref 1-D982OQU), both for the same underlying condition
  (Bill Limit below configured Agent Minimum). Message format: `"Bill Limit can not be set lower
  than Agent Minimum [N] Please Contact the System Administrator with Reference #
  [order-ref].(SBL-EXL-00151)"`. Resolution path stated in-message: **contact the System
  Administrator** (i.e., no self-service override for the agent role in this scenario) —
  neither source shows what the System Administrator does next; **[GAP]**.
- **Non-blocking advisory.** "Note: Maximum Bill Limit is equivalent to account Credit Limit.
  Please communicate this to customer." Fires on Validate regardless of outcome in both sources;
  does not stop the flow, is an agent-facing reminder to relay the ceiling to the customer.
- **BL RULE 01/02/03 (in-flight/conflict exceptions)** — all block order progression outright
  ("Cannot Proceed!"); no override path is documented in the source corpus. **[GAP: no evidence
  of an override/escalation UI for these three specifically.]**
- **BL RULE 07 (exceeds Credit Limit)** — blocks; the fix implied by the message and the
  companion advisory is to lower the requested Bill Limit to at or below the account's Credit
  Limit (which, per source #5, is itself an editable/escalatable value elsewhere in the
  account/order flow).
- **BL RULE 08/09 (blank / invalid number)** — standard client-side format validation, blocking,
  self-correctable by the agent without escalation.
- **Order remains Pending after failure.** In both directly observed cases (sources #3, #4), the
  order is left in Pending status after the blocking dialog is dismissed; no screenshot shows a
  subsequent correction attempt, resubmission, or abandonment specifically for the Bill Limit
  failure (contrast with source #4's account history showing two *unrelated* prior Pre2Post
  orders already Abandoned on the same account, which is incidental context, not evidence of how
  a Bill-Limit-specific rejection is remediated).

## Data Inputs/Outputs

**Inputs:**
- MSISDN / target installed asset (Mobile Service Bundle) identifying which line's Bill Limit is
  being changed [catalogue Description, sources #1/#2]
- New Bill Limit value ("SL Limit Amount") entered by the agent [sources #3 step 8, #4 step 10]
- Bill Limit product selection (e.g. "Bill Limit Mobile" vs. "Bill Limit Mobile Plus") — each
  carries its own configured SL Min Value, SL Default Value, and Agent Min Value [sources #3
  step 3, #4 step 3]
- Account Credit Limit (read, used as the upper-bound check; itself editable elsewhere per
  source #5 — dropdown of preset values 0/50/200/500/800/1000/1500/2000)
- Existing in-flight/open orders on the account (read, used for BL RULE 02/03 conflict checks)
- Existing Paid Add-Ons on the current order (read, used for BL RULE 01 check)

**Outputs:**
- Updated Bill Limit / SL Limit Amount value attached to the Mobile Service Bundle line item, on
  success
- Modification order status: Pending → (on validation failure) remains Pending with an error
  dialog; → (on validation success, **[INFERRED]**) proceeds to submission/Complete
- Blocking or informational dialog text surfaced to the agent (SBL-EXL-00151 / BL RULE 01-09
  messages / Credit-Limit advisory), which the agent is expected to relay to the customer where
  relevant (per the explicit advisory text)
- Siebel error reference number (e.g. 1-DAFQWTQ, 1-D982OQU) for administrator follow-up on
  blocking failures
