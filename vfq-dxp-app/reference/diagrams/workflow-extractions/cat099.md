## Journey Overview

Catalogue #99 sits inside the broader MNP (Mobile Number Portability) port-out process. The catalogue-level description frames the CRM-agent-facing slice of this process: an agent works a trouble ticket (TT) that was auto-created when a customer initiated a port-out at a competing operator, updates the ticket's **Activity Status** as validation/approval steps are completed, and submitting the ticket at the terminal status is what triggers the actual port-out on the Vodafone side. Both Day9 sessions describe the wider end-to-end mechanics (NPAS integration, auto-validation, conditional acceptance, manual penalty calc) that determine what activity statuses get set and why.

Scope note: this extraction covers **consumer port-out** only, per source Day9-Session2 [00:03:12] ("Stated for consumer") and the CRM Journeys catalogue's CBU=Yes/EBU=No flag for row 99. B2B2C/enterprise variants are mentioned only where the source explicitly contrasts them (flagged inline).

## Workflow Steps (numbered)

1. **Trigger — customer initiates port-out at recipient operator.** Customer goes to a competing operator (stated as Ooredoo/QTEL, the only donor/recipient named in this corpus), signs a CAF there, and sends a consent SMS. [Day4S2 01:08:03; Day9S2 00:03:02]
2. **NPAS notification.** The SMS/request goes to NPAS ("Enpass"/"N-POS" in the transcripts), the government-managed inter-operator porting system. NPAS notifies Siebel of the port-out request. [Day9S2 00:03:02; Day4S2 01:02:14, 01:08:19]
3. **Auto-creation of the trouble ticket.** Siebel automatically creates a trouble ticket and routes it to a dedicated MNP queue. No agent action initiates this step. [Day4S2 01:02:14; Day9S2 00:03:02]
4. **Auto-population of ticket data.** On creation, the system auto-fetches certain fields onto the ticket: unbilled amount, and plan-locking/commitment-penalty indicator. DOI (outstanding) amount is explicitly **not** auto-fetched. [Day4S2 01:02:28]
5. **System auto-validation (automated, no agent).** Siebel automatically validates: customer name, QID/ID type and number, service type, and consumer type against system records. [Day9S2 00:16:00]
   - If any of these fail, the system **auto-rejects** the ticket without it ever reaching the fulfilment team. [Day9S2 00:18:02]
   - Only requests that pass all auto-validation checks reach a human. [Day9S2 00:18:02]
6. **Suspension/bar check (automated).** If the customer's account is suspended/barred, the ticket is automatically rejected with reason "requested number is suspended or barred." [Day9S2 00:22:13]
7. **Blacklist / low-outstanding check (automated, logged as activities).** Automated checks — customer has low outstanding value, customer is not blacklisted — are recorded as ticket **activities**, preserving a visible history of why a TT was accepted or rejected. [Day4S2 01:11:21]
8. **Star-number commitment block (automated control).** If the number is a "star number" (high-value number) still inside its commitment period, a configurable control blocks the port-out. Built specifically after customers took high-value star numbers and immediately ported out. [Day4S2 01:05:12–01:05:36]
9. **Conditional acceptance check — billed due threshold (automated, consumer).** If the customer's **billed** due amount exceeds 100 QAR (Riyal), the ticket is automatically set to a conditional-acceptance / "Failure" status rather than outright accepted. Unbilled amounts do **not** trigger this — only billed (i.e., invoiced-but-unpaid) amounts count. [Day9S2 00:20:15, 00:20:26, 00:20:39]
   - If conditionally accepted, the customer has a payment window to clear the billed due (stated elsewhere in the corpus, Day9S1, as ~8 business hours presented to the customer as 24 hours for the related port-in flow; for port-out the ticket's own SLA clock governs, see Step 11).
10. **Manual document/signature validation (agent, MNP/Porting team).** Because Siebel cannot read the digitally signed MNP form or verify signatures, and because those documents live only in NPAS (not in Siebel), the agent manually retrieves the form/ID from NPAS and checks: signature, form date (must be within the past 30 days of signing), segment (consumer vs. business), product/service (prepaid/postpaid, correct in Vodafone's own records), customer name, ID number, and the requested mobile number. [Day9S2 00:11:42, 00:14:28, 00:18:29, 00:25:56]
11. **Two-hour SLA action window (agent).** Once the ticket lands with the team, the fulfilment/MNP agent has 2 hours to validate and act (accept/reject/conditionally accept). If documents have been validated but final action is pending, the window is extended to 24 hours. Both windows are bound by NPAS's operating hours (~7:30–15:30/16:00) as a hard stop rather than a rolling SLA — requests outside those hours roll to the next day. [Day9S2 00:03:15, 00:09:46, 00:29:01]
12. **Agent updates Activity Status on the ticket.** This is the catalogue-#99-defining action: the agent records the outcome of validation/approval steps (auto-checks passed, documents validated, conditional-acceptance outcome, payment received, etc.) as Activity Status updates inside the TT. [CRM Journeys row 99; pattern corroborated by Day4S2 01:11:21's "activities" logging]
13. **Manual penalty/dues calculation (agent, only when applicable).** Commitment/plan penalty, device dues, and star-number penalty/locking charges are **unbilled** amounts and therefore cannot block the port-out; they are calculated manually by the agent and are not enforced as a gate. [Day9S2 00:23:03; Day4S2 00:57:56, 01:03:56]
14. **Agent submits the ticket post activity-status update.** Submitting the ticket at the appropriate terminal activity status is what auto-triggers the port-out on the Vodafone side. [CRM Journeys row 99]
15. **Payment validation, if conditionally accepted (automated).** If the customer pays the billed due during the conditional-acceptance window, the system automatically validates the payment against the billing profile and the ticket, and (for consumer) the request proceeds without further manual intervention. [Day9S2 00:21:58, 00:27:04]
    - Exception: for B2B2C, status must be **manually** changed to Approved after payment because it is treated as enterprise. [Day9S2 00:27:04] (noted as a contrast case, not in scope for the consumer-only catalogue #99 flow, but material to the decision logic.)
16. **Porting execution.** On approval, NPAS coordinates both operators; Vodafone's side disconnects/releases the number and the recipient operator connects/activates it during the shared porting window. (Porting-window mechanics — Sunday–Thursday, 11:00–12:00 — are documented for port-in in Day9S1 and referenced as the same NPAS-governed mechanism; not independently re-confirmed for port-out in these three sources, so treated as inferred/shared infrastructure rather than a port-out-specific fact.) [Day9S1 general MNP mechanics; Day4S2 01:08:03]
17. **Final bill / dunning.** After port-out completes, the team calculates the manual penalty (Step 13) and adds it as a pro-rated final invoice/final bill based on months completed under commitment. [Day9S2 00:23:25]
18. **Rejection outcome (any gate fails).** If any automated check, manual validation, or conditional-acceptance payment fails, the ticket is rejected with one of ~14–15 NPAS-mapped rejection-reason codes (consumer uses only reasons "one, four and nine" of that set — the corpus does not enumerate the reason text, only the ordinal positions). The number stays with Vodafone. [Day9S2 00:05:58, 00:30:41, 00:31:15; Day4S2 01:07:55]

## Exception Handling

- **Auto-rejected on identity/service/consumer-type mismatch** — ticket never reaches a human; customer would need to restart the port-out request from the recipient operator (not detailed in these sources; inferred from the "restarts the whole MNP journey on rejection" rule documented for port-in in Day9S1, extended here as a reasonable analogy — **flagged as inferred, not directly confirmed for port-out**).
- **Star-number commitment block** — hard stop while inside commitment period; no override path is described in the sources (flagged as unknown whether any manual override/exception process exists).
- **Conditional acceptance / unpaid billed due** — customer given a payment window; if unpaid, ticket presumably lapses/rejects, but the exact system behavior at window expiry is not stated in these three sources (flagged unknown).
- **B2B2C manual status change after payment** — an explicit deviation from the consumer auto-flow: agent must manually move status to Approved. [Day9S2 00:27:04] (out of scope for catalogue #99's consumer/CBU framing but noted since it's the one documented exception to automation.)
- **Documents not machine-readable** — Siebel cannot validate the digital MNP form or signature; agent must go into NPAS directly to view/validate. A requirement was raised (not yet built) to bring these documents into Siebel as ticket attachments. [Day9S2 00:12:46]
- **Manual penalty calculation gap** — plan/commitment penalty, device dues, and star-number/locking charges cannot block port-out (they're unbilled) and are calculated manually post-port-out rather than enforced as a gate; a business requirement was raised to automate this calculation. [Day9S2 00:23:03, 00:40:29; Day4S2 01:03:56 — also raised: no system record linking the star-number penalty to the specific port-out request, a named gap]
- **Manual ticket distribution** — MNP tickets are not auto-assigned to individual agents; a team lead exports ~200–300/day from the queue, splits into Excel, and emails agents, who then self-assign in Open UI (bulk owner-change is a documented workaround). This is a process pain point, not a per-ticket branch, but materially affects how/when Step 11's SLA clock gets acted on. [Day4S2 01:22:22; Day9S2 00:35:01, 00:35:23]

## Business Rules

- **BR-1 (SLA):** Fulfilment team has 2 hours to act on an auto-created port-out ticket; extends to 24 hours once documents are validated. Both windows are hard-stopped by NPAS working hours (~7:30–15:30/16:00), not a rolling clock — requests outside those hours roll to the next day. [Day9S2 00:03:15, 00:09:46]
- **BR-2 (Conditional acceptance threshold, consumer):** Billed due > 100 QAR triggers automatic conditional acceptance. Unbilled amounts never trigger this for MNP (contrast: FNP does allow unbilled amounts to trigger conditional acceptance, and FNP operates at service level rather than MNP's billing-profile level). [Day9S2 00:20:15, 00:20:26, 00:39:46]
- **BR-3 (Star-number port-out block):** Star (high-value) numbers are blocked from porting out during their commitment period; control is configurable. Built after abuse pattern (customers taking star numbers then immediately porting out). [Day4S2 01:05:12]
- **BR-4 (Auto-fetch scope):** Only unbilled amount and plan-locking/commitment-penalty flag are auto-fetched onto the ticket; DOI outstanding amount is not auto-fetched. [Day4S2 01:02:28]
- **BR-5 (Penalty automation gap):** Only plan/long-term-commitment penalties are automated; star-number and device penalties remain manual business rules the agent must check (a separate, not-yet-delivered project is automating these). [Day4S2 00:57:56, 01:03:56]
- **BR-6 (Auto-validation scope):** System auto-validates customer name, QID/ID type+number, service type, and consumer type; auto-rejects on any failure before human involvement. [Day9S2 00:16:00, 00:18:02]
- **BR-7 (Manual document checklist):** MNP form validity = 30 days from signature date; segment, product/service, name, ID, and requested number are manually checked against the form retrieved from NPAS. [Day9S2 00:14:28, 00:25:56]
- **BR-8 (Rejection reason coupling):** ~14–15 rejection reason codes are tightly coupled to NPAS by agreement and cannot be renamed/changed unilaterally; consumer segment uses only 3 of them (referred to as "one, four and nine" — ordinal position only, exact text not in source). Free-text explanation goes in a ticket-level comment, not the code itself. [Day9S2 00:05:58, 00:30:41, 00:31:15, 00:31:43]
- **BR-9 (B2B2C exception):** For B2B2C, ticket status must be manually changed to Approved after payment (vs. consumer's automatic proceed). [Day9S2 00:27:04]
- **BR-10 (Scope):** This corpus states the port-out ticket flow "for consumer" specifically [Day9S2 00:03:12]; catalogue #99 itself is flagged CBU=Yes / EBU=No, consistent with this scope.

## Data Inputs / Outputs

**Inputs to the ticket / process:**
- Port-out request notification from NPAS (customer identity, requested MSISDN, recipient operator = Ooredoo/QTEL)
- Auto-fetched: unbilled amount, plan-locking/commitment-penalty flag
- Manually retrieved from NPAS: signed MNP form (date, segment, product, name, ID, requested number), donor-registered ID
- System-of-record data for validation: customer name, QID/ID type+number, service type, consumer type, account suspension/bar status, blacklist status, star-number flag + commitment-period end date
- Agent-entered: Activity Status updates, manual penalty calculation values (commitment/plan penalty, device dues, star-number/locking charges)

**Outputs from the process:**
- Ticket activities log (records of automated checks: low outstanding, not blacklisted) — visible audit trail of why a TT passed/failed [Day4S2 01:11:21]
- Rejection reason code (mapped to NPAS's 14–15 code set) + free-text ticket-level comment, when rejected
- Conditional-acceptance / "Failure" status with pending-payment state, when billed due > 100 QAR
- Port-out execution trigger to NPAS/Siebel on ticket submission at terminal activity status
- Final bill / final invoice with pro-rated manual penalty, issued after port-out completes
- Customer-visible ticket status (open/closed) and resolution, viewable in the customer app (view-only; customer cannot reopen or create these tickets) [Day4S2 01:12:52, 01:13:11]
