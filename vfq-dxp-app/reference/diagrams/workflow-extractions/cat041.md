## Journey Overview

**Trigger:** A Care/Retail agent, while working an existing customer account for a specific MSISDN (mobile number) in Open UI/Siebel ("Vanilla" desktop CRM), determines that the customer's issue/request needs to be logged as a formal Trouble Ticket (TT) — either because inbound troubleshooting on the Complaint Management Process did not resolve the issue, or because a system/customer-originated request needs an agent-created ticket (source evidence 1, 2).

**Actors:**
- **Care Agent / Front-line (Care/Retail) Agent** — primary actor, creates and submits the ticket (source 1, 2 — slide 17/18 screenshots show agent "ANUJYADAV" as Created By/Owner).
- **Customer** — contacts Vodafone via call/email/chat/visit (or MVA app, which does not create a ticket directly but sends a report to a team to raise one) (source 1, source 2 slide 16 flowchart).
- **System (auto-assignment engine)** — routes a submitted ticket to a queue based on Source/TT Category/Area/Sub-Area/Language/Customer Type (source 2 slide 21).
- **Team/Queue owner (e.g., Complaints Team, MNP Team, Retention Team, CDM team)** — downstream consumer of the queued ticket; out of scope for ticket *creation* itself but is the routing destination (source 1, source 2 slide 21).

**Systems:** Open UI (agent-facing CRM front end used for ticket creation, described as "Vanilla" desktop channel for this journey), Siebel (backend, LOV source `VFQA_TT_HASHTAGS` / `VFQA_TT_ACTUAL_ISSUE`), MVA (My Vodafone App — customer-originated requests, does not write tickets directly), NPAS/eShop/Portal (other system-generated ticket sources, not agent-created) (source 1).

## Workflow Steps (numbered)

1. **Customer contact for an issue.** Customer contacts Vodafone via inbound call, email, chat, or in-person visit (source 2, slide 16 "Complaint Management Process" flowchart: Customer lane → "Customer contact VF for an issue").
2. **Agent receives and troubleshoots.** Front-line (Care/Retail) agent receives the inbound contact and performs troubleshooting (source 2, slide 16: "Receives Inbound Call/email/Chat/Visit" → "Troubleshooting").
3. **Decision: Is the issue resolved?** If YES, agent communicates resolution to customer and the interaction ends without a ticket (source 2, slide 16: "Issue resolved" diamond → YES → "Communicate Resolution to the Customer" → "Receive Feedback" → END). If NO, proceed to ticket creation (source 2, slide 16: NO branch → "Create TT & Submit with correct type").
4. **Agent navigates to Trouble Tickets list (within the Customer Account for the specific MSISDN).** Agent opens the Trouble Tickets applet/list view on the account, which already shows existing tickets for that MSISDN (Priority, Status, Ticket ID#, Order#, MSISDN, Date Opened/Closed columns) (source 2, slide 17/18 screenshot, image57.png).
5. **Agent clicks the "+" (New) icon** on the Trouble Tickets list to create a new ticket record (source 2, slide 17 screenshot, image57.png — the "+" icon is highlighted).
6. **New ticket record opens** with a system-generated Ticket ID (e.g., "1-228139191579"), Date Opened auto-stamped, Status defaulting to "Not Solved" (source 2, image58.png/image61.png).
7. **Agent populates Ticket Information fields**, including (per the ticket form screenshot, image61.png):
   - Last Name / First Name / Account / Service Location (auto-populated from the customer account context)
   - **MSISDN** (the specific mobile number the ticket is being raised against — matches the catalogue description "for Specific MSISDN")
   - Contact Role, SIM, Account #, Tier, **Customer Type** (e.g., "Reimbursement"), Service Type, Asset Service Type
   - TON Reason / MOI Reason (conditional fields for specific ticket types)
   - Plan, Appointment Id, NP Order Id (contextual, populated only for certain ticket types)
8. **Agent selects ticket categorization fields** — **Source**, **TT Category**, **Area**, **Sub-Area** dropdowns (source 2, image61.png "TT Category / Area / Sub-Area" block) — these are the fields that, combined with Language and Customer Type, drive auto-assignment to a queue (source 2, slide 21 routing table).
9. **Agent enters Coordinates/Address/Landmark/Latched Site ID/Zone-Area** where applicable (network/location-relevant tickets) (source 2, image61.png).
10. **Agent selects Language** (e.g., Arabic/English) — also a routing-table input (source 2, image61.png, slide 21).
11. **Agent selects Priority and Severity** (e.g., "3-Medium" / "4-Low" observed defaults) (source 2, image61.png).
12. **Agent enters a Description** of the issue/request in free text (source 2, image61.png).
13. **Agent selects the Hashtag** from the `VFQA_TT_HASHTAGS` LOV dropdown (454 possible values spanning network/technical, billing/adjustment, customer-ops, device/campaign, and "CCT-" Contact-Centre-Ticket sub-codes) (source 3; field location confirmed in source 2, image61.png "Hashtag" dropdown, highlighted).
14. **Agent selects the TT Actual Issue** from the `VFQA_TT_ACTUAL_ISSUE` LOV dropdown (355 possible values, largely billing/account-servicing root causes plus a "CCT-" request/dispute family) (source 3; field location confirmed in source 2, image61.png "TT Actual Issue" dropdown, right column under Status and Ownership).
15. **Fields auto-populate under "Status and Ownership":** Created By, Login, Location, Previous Owner, Owner — all auto-stamped to the logged-in agent at creation time (source 2, image61.png).
16. **Agent clicks "Assign To Me"** (optional/contextual — only works if the agent is a member of that ticket's eventual queue's user list; button is shown active pre-submission in the screenshot) (source 2, image61.png "Assign To Me" highlighted; source 1: "'assign to me' only works if the agent is in that queue's user list").
17. **Agent clicks "Submit."** This is the terminal creation action — a ticket that is created but never submitted does NOT route to any queue (source 1: explicit business rule "a ticket created but not submitted does not route to any queue"; button visible in image61.png toolbar).
18. **System auto-assigns the submitted ticket to a Queue.** Based on the combination of Source / TT Category / Area / Sub-Area / Language / Customer Type, the system looks up a matching row in the routing table and stamps the ticket with a TT Queue (e.g., `VFQA_CMT_BULK_NEW_TICKETS_QUEUE`, `VFQA_FIXED_QUEUE_CONSUMER`, `VFQA_CHANNEL_COMPLAINTS_QUEUE_COPS`, `VFQA_DOHA_CMT_NEW_TICKETS_QUEUE`, `VFQA_FIXED_QUEUE_INSTALLATION`) (source 2, slide 21 routing table). Assignment is at team/queue level, not to an individual agent, and there is no automatic reassignment on delay (source 1).
19. **Ticket activities are created/logged** as the ticket progresses (SMS notifications, back-office calls, escalations, resolutions) visible in the "Activities inside Tickets" grid — Created/Owner/Activity#/Account/Channel/Topic/Sub-Topic/Type/Area/Language/Interaction Type/Comments/Status columns (source 2, slide 19 screenshot, image62.png). This is downstream of ticket creation (post-submission ticket lifecycle) but confirms the ticket record continues to accrue structured activity records after queue assignment.

## Exception Handling

- **Unsubmitted ticket:** A ticket that is created but not submitted does not route to any queue at all — it is effectively orphaned (no queue, no owner-team visibility) (source 1). No documented remediation/alert for this state was found in the source material — flagged as a gap.
- **"Assign to Me" queue-membership mismatch:** clicking Assign To Me only succeeds if the agent belongs to the destination queue's user list; source material does not describe the UI's behavior when this fails (silent no-op vs. error message) — flagged as a gap/unknown.
- **No automatic reassignment on delay:** once queued, a ticket does not automatically reassign if it sits unactioned; this is called out as a current-state limitation, and "enhanced auto-assignment" / "automatic escalation" appear later as **proposed** (not yet built) enhancements (source 2, slide 37 Summary).
- **Ticket LOV additions require a system release** — dynamic ticket LOV management (i.e., being able to add a new Hashtag/Actual Issue/Category value without a release) is listed as a current-state gap, addressed only in the proposed-enhancements list, not the as-is flow (source 1: "dynamic ticket LOB management (currently new LOBs require a release)"; source 2 slide 37: "Dynamic Ticket LOV Management" proposed enhancement).
- **Customer cannot reopen a ticket from the app** — only an agent can reopen; not part of the creation flow itself but a related lifecycle constraint (source 1).
- **Special/complex ticket sub-journeys** (End Data Session, Transfer of Number, Disconnection, MNP Port-Out) have their own auto-creation and additional-approval logic layered on top of the generic creation form described here; these are explicitly scoped to separate follow-up sessions and are NOT re-derived in this extraction beyond noting they exist as ticket "types" selectable via TT Category/Area (source 1).

## Business Rules

- BR1 — Tickets are assigned at **team/queue level**, never at individual-agent level, and there is no automatic reassignment on delay (source 1).
- BR2 — A ticket **not submitted does not route to any queue** (source 1).
- BR3 — Queue auto-assignment is computed from the combination **Source × TT Category × Area × Sub-Area × Language × Customer Type** (source 2, slide 21 routing table; 5 example rows extracted verbatim).
- BR4 — **"Assign to Me"** only functions if the agent is already a member of the target queue's user list (source 1).
- BR5 — **Ticket sources** recognized by the system: agent-created (this journey), system-generated (from eShop/NPAS/portal), Open UI Excel (bulk upload), and customer-originated via MVA — but MVA requests land in a validation/report queue and must still be turned into an agent-created ticket, not created directly by the customer (source 1; source 2 slide 15: "Currently the customer can create requests from MVA which is being sent as report to a Team to contact customer and raise tickets in System").
- BR6 — **Each ticket/issue type has a specific template** that the agent fills in and pastes into the Open UI Ticket Fields (source 2, slide 15 note, verbatim: "Note: All the type of tickets and issues are having a specific template wherein agents have to fill the details and paste it in Open UI Tickets Fields").
- BR7 — Ticket categorization fields (**Hashtag**, **TT Actual Issue**) are drawn from fixed, centrally-managed Siebel LOVs — `VFQA_TT_HASHTAGS` (454 active values) and `VFQA_TT_ACTUAL_ISSUE` (355 active values) — both currently require a system release to extend (source 3; source 1 "dynamic ticket LOB management" gap).
- BR8 — **A customer cannot reopen a ticket** from the app; only an agent can (source 1).
- BR9 — **SMS content tied to tickets is controlled within teams**, both for automated (New Ticket, Re-Opened Ticket) and manual SMS sends, and a manual SMS send itself creates a logged ticket Activity (source 2, slides 20 and 22).
- BR10 — Audit trail exists on tickets/account tabs but is **role-restricted from agents** (visibility gap, not creation-blocking, but relevant to who can see what post-creation) (source 1).
- BR11 — Current in-system SLA for tickets is a **flat 24 hours** with no segregation between request-type and complaint-type tickets today — segregation is only a proposed enhancement (source 1; source 2 slide 37 "Ticket Segregation").

## Data Inputs / Outputs

**Inputs (agent-entered or context-carried into the form):**
- Customer/Account context: Last Name, First Name, Account, Service Location, Account #, Tier, Contact Role, SIM (from Customer Account for the specific MSISDN)
- **MSISDN** (the specific mobile number — required per catalogue description)
- Customer Type (e.g., Reimbursement)
- Source, TT Category, Area, Sub-Area (categorization/routing inputs)
- Coordinates, Address/Landmark, Latched Site ID, Zone/Area (location context, ticket-type dependent)
- Language (routing input)
- Priority, Severity (defaults observed: 3-Medium / 4-Low)
- Description (free text)
- Hashtag (from `VFQA_TT_HASHTAGS` LOV)
- TT Actual Issue (from `VFQA_TT_ACTUAL_ISSUE` LOV)
- TON Reason / MOI Reason / Plan / Appointment Id / NP Order Id (conditional, ticket-type-specific fields)

**System-generated / auto-populated:**
- Ticket ID (e.g., "1-228139191579")
- Date Opened, Date Modified (timestamps)
- Created By, Login, Location, Previous Owner, Owner (stamped to submitting agent)
- Status (defaults "Not Solved"), Sub-Status ("Unassigned")

**Outputs:**
- A submitted Trouble Ticket record, stamped with a system Ticket ID, visible on the account's Trouble Tickets list
- **TT Queue** assignment (system-computed from the routing table — e.g., `VFQA_CMT_BULK_NEW_TICKETS_QUEUE`, `VFQA_FIXED_QUEUE_CONSUMER`, `VFQA_CHANNEL_COMPLAINTS_QUEUE_COPS`, `VFQA_DOHA_CMT_NEW_TICKETS_QUEUE`, `VFQA_FIXED_QUEUE_INSTALLATION`)
- Downstream ticket Activities begin accruing (SMS notifications, back-office calls, escalations) once the ticket is live in a queue

## Gaps / Unknowns (explicitly flagged)

- The **UI behavior on a failed "Assign to Me"** (queue-membership mismatch) is not described — no error text captured.
- The **specific template content per ticket type** (referenced in BR6) was not located in this corpus; source only confirms templates exist and are pasted into ticket fields, not their contents.
- Whether **priorities are actually used to affect assignment/SLA in the as-is system** is an open question the workshop itself left unresolved (source 1: "whether priorities will be used in to-be design (not used today)" — implies priority field exists on the form but may not be functionally load-bearing today).
- The four sequential-approval, End Data Session, Disconnection, and MNP Port-Out special ticket sub-flows are **out of scope** for this extraction (they are auto-created or have additional gates) and are documented in source 1 as slated for separate dedicated sessions — not re-derived here.
