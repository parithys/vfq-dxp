## Journey Overview

**Trigger:** A CSR/Agent (or the customer's servicing need) requires the account's Credit Limit to change — either mid-activation (as captured in the HRN guided journey, where the default pre-approved limit is overridden before contract generation) or as a standalone post-activation "Manage" action against an existing account (the #136/#146/#147 catalogue framing: "Value Updates in Existing Fields Based on Responsibilities," delivered today via Vanilla/Open UI Desktop rather than a dedicated guided wizard).

**Actors:**
- **CSR/Agent** — performs the edit for consumer (CBU) accounts, role-gated (per the PMN/suspension precedent in Day2 Session2, credit-limit-affecting actions are "restricted to specific roles")
- **Business Finance (approval role)** — required approver for enterprise (EBU) accounts; no default credit limit exists for EBU, so any enterprise credit limit requires this sign-off before it takes effect (Day 11 Session 1)
- **System (Siebel/Open UI order-validation engine)** — enforces BL RULE 01–09 and related credit-limit/deposit rules at save/submit time

**CBU vs EBU branch:** For consumer (CBU) accounts, the credit limit has a pre-approved default (e.g., 800 for the Expatriate/Qatari HRN case) and the CSR/Agent can edit it directly through a role-gated dropdown control with no further sign-off shown in the evidence. For enterprise (EBU) accounts, there is no default credit limit at all, and Day 11 Session 1 states plainly that establishing/changing it "requires business finance approval" — i.e. the same underlying "update credit limit" capability forks into a direct edit path (CBU) vs. an approval-gated path (EBU).

**Unknowns flagged explicitly:**
- No source document shows the EBU finance-approval UI/queue mechanics step-by-step (no Guided Journey exists for enterprise credit-limit approval — Guided journey Desktop/Tablet = No for all three catalogue rows). The approval gate is corroborated only at the level of the Day 11 Session 1 statement; the concrete approval workflow (who requests it, SLA, system screen) is not evidenced and is not invented here.
- The exact list of "specific roles" permitted to edit credit limit is not enumerated in any source (Day2 Session2 says "restricted to specific roles" for the related PMN/zero-credit-limit action, without naming the roles).
- BL RULE 06 does not appear in the source workbook (the rule numbering jumps 05 → 07); this is reported as a gap, not filled in.
- Whether the same dropdown-of-preset-values mechanic (0/50/200/500/800/1000/1500/2000) applies to EBU accounts, or whether EBU credit limits are free-text/finance-set values, is not shown in any source.

## Workflow Steps (numbered)

1. **Trigger — credit limit change needed.** CSR/Agent opens the customer's Account (existing account, e.g., via Account 360 / Vanilla Open UI Desktop) or is mid-way through a New Postpaid activation guided journey and reaches the Plan/Account step where the current (default or pre-approved) credit limit is displayed. [Guided Journey HRN Credit Limit]
2. **Decision — Enterprise (EBU) account?** System/process branches based on account business type (CBU consumer vs. EBU enterprise), captured at account creation as "business type (including B2B2C)". [Business Process Day11 Session1]
   - **No (CBU/consumer):** proceed to step 3.
   - **Yes (EBU/enterprise):** proceed to step 3a (finance approval branch).
3. **(CBU path) Agent opens "Edit Credit Limit" control.** In the Plan step of the order/account, the current credit limit is shown (e.g., "Credit Limit: 800" for a Pre-approved Expatriate/Qatari default) alongside an "Edit Credit Limit" button. [Guided Journey HRN Credit Limit]
4. **(CBU path) Agent selects new value from preset dropdown.** Options observed: 0, 50, 200, 500, 800, 1000, 1500, 2000. Agent selects a new value (e.g., 1000) and clicks "Go." [Guided Journey HRN Credit Limit]
5. **(CBU path) System validates the new value against order-validation business rules** — including BL RULE 05 (not below configured minimum), BL RULE 07 (Bill Limit cannot exceed Credit Limit — validated the other direction whenever a Bill Limit product/value coexists on the account), BL RULE 08 (limit field cannot be blank), BL RULE 09 (must be a number ≥ 0), and BL RULE 01/02/03 (in-flight-order conflict checks — a Bill Limit modification must be a separate order if paid add-ons are present, and cannot proceed if another in-flight order is already adding/updating the Bill Limit or a paid add-on). [Order Validation Business Rules]
6. **(CBU path) Panel updates to reflect new Credit Limit** (e.g., "Credit Limit: 1000"). [Guided Journey HRN Credit Limit]
7. **(CBU path) Value propagates downstream** — onto the generated CAF ("Account credit limit: 1000"), onto the Sales Order record ("Credit Limit: 1,000" on the order's Credit Control rail), and back onto the Account's pre-approved credit-limit field once the order completes/saves. [Guided Journey HRN Credit Limit]
3a. **(EBU path) Agent/account manager submits the desired credit limit for the enterprise account.** Since enterprise accounts carry no default credit limit, any value must be established or changed through this path. [Business Process Day11 Session1]
4a. **(EBU path) Decision — Business Finance approval obtained?** Enterprise credit-limit changes require Business Finance sign-off before taking effect. [Business Process Day11 Session1]
   - **No (not yet approved):** change remains pending / does not take effect (exact system state not evidenced — flagged as unknown).
   - **Yes (approved):** proceed to step 5a.
5a. **(EBU path) Credit limit is applied to the enterprise account**, subject to the same downstream order-validation rules noted in step 5 wherever a concurrent Bill Limit/paid-add-on order exists. [Order Validation Business Rules, inferred continuity from CBU mechanics — not separately evidenced for EBU]
8. **End — Credit Limit Updated** on the account (and reflected on any open/related order line items).

## Exception Handling

- **BL RULE 01** — "Bill Limit Modification to be done in a separate order as Paid Add-Ons are present in this Order!" — if paid add-ons exist on the current order, a Bill Limit/credit-limit-linked change must be split into its own order.
- **BL RULE 02** — "Inflight order Adding/Updating Bill Limit found. Cannot Proceed!" — blocks a second concurrent Bill Limit change while one is already in flight.
- **BL RULE 03** — "Inflight Order adding Paid Addon found. Cannot Proceed!" — blocks the change if a concurrent order is adding a paid add-on.
- **BL RULE 04** — "Cannot Proceed! Please Update Bill Limit to a higher value." — raised when the requested Bill Limit is too low relative to some other constraint.
- **BL RULE 05** — "Bill Limit cannot be set lower than configured minimum amount. Please set to above configured minimum value or choose the other Bill Limit product." — minimum-threshold guard.
- **BL RULE 07** — "Bill Limit Value cannot be more than Credit Limit!" — the core cross-field rule tying Bill Limit to Credit Limit; a Bill Limit change (or, by the same cross-check, a Credit Limit reduction) that would put Bill Limit above Credit Limit is rejected.
- **BL RULE 08** — "Bill Limit Cannot be left blank." — mandatory-field guard.
- **BL RULE 09** — "You have entered an incorrect Limit Amount! Please ensure to only enter a number greater than or equal to 0!" — numeric/non-negative guard.
- **Deposit/credit-limit product consistency (BUSINESS RULE 122–125 / ORD_VALD_RULE_142–144, 150)** — for deposit/credit-limit-linked products, the billing profile must be Active and Postpaid ("BP is not Postpaid or Active. Please select a valid Billing Profile"), and Order Header, OLI (Order Line Item), Billing Profile, and Service Account must all be consistent; purchase of legacy deposit-for-credit-limit products (Deposit 100/500/1000 for Credit Limit) is blocked in favor of the current Deposit Service Bundle product.
- **iWatch/RIO credit check (BUSINESS RULE 9 / ORD_VALD_RULE_042)** — "Can't Proceed with RIO Activation of: $TotAmt with Account Balance: $SurepayBalance" — a related but distinct credit-limit-adjacent check blocking iWatch bundle activation if recurring amount exceeds account balance.
- **Not evidenced / flagged as unknown:** the specific rejection/notification path when Business Finance does not approve an enterprise credit-limit change (no source shows this state).
