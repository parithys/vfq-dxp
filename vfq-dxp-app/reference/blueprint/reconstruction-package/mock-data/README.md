# Mock Data (Phase 27) — Comprehensive Seed Dataset

**Classification: Assumed / Synthetic.** Every value in this folder (names, QIDs, phone numbers, order IDs,
amounts) is fabricated for demo/seed purposes. No real customer data exists anywhere in the source corpus,
nor should it — this is expected and intentional for a front-end-only application with no backend.

What IS evidence-grounded: the **field/attribute structure** of each record type, taken from
`../../domain-model.md`'s entity catalogue. Every file below is traceable to a specific `ENT-xxx` entity —
open `domain-model.md` and search for that ID for the full evidenced attribute list and source citations.

## Coverage

**74 files, 226 records, covering all 77 of 83 domain entities that are actual mockable business records** — 100% of the mockable set. The other 6 of 83 are meta/reference constructs intentionally excluded (not missing — already represented elsewhere in the blueprint): ENT-061 CRM Journey/Feature Catalog, ENT-062 Functional Cluster, and ENT-063 Type Taxonomy Category are covered by `module-hierarchy.md`; ENT-076 Data Field is `field-inventory.md`; ENT-077 Status Model is `screen-state-model.md`; ENT-082 Customer 360 is a computed aggregation view over other entities, not a stored record type.

## Scaling this dataset further

This is still a **seed set** (2-4 records per entity), sized to illustrate structure and support manual QA of
each journey/screen end-to-end, not to simulate production data volume. For real development, the Mock Data
Engine (see `../docs/frontend-architecture.md` §7) should generate larger synthetic volumes programmatically
(e.g. via a faker-style generator seeded from these same field definitions) rather than hand-authoring
hundreds of JSON records per entity.

## Cross-referencing

Records across files use consistent IDs where a real-world relationship exists — e.g. `adjustments.json`'s
`ADJ-8001` references `billing-profiles.json`'s `BILL-7001` and `customers.json`'s `CUST-1001`;
`enterprise-accounts.json` introduces a new parent-account tier (`ENT-ACC-77xx`) above the existing
`accounts.json` sub-accounts (`ACC-5003`, `ACC-5004`) to demonstrate the evidenced Enterprise parent/sub-account
hierarchy. Not every cross-reference is exhaustively wired — treat this as a realistic starting graph, not a
referentially-complete database.

## Known limitation

The 6 files generated in the same batch as another (see the batch groupings in the Stage J generation log) were
produced by a single agent call per ~9 entities for efficiency — cross-entity ID consistency is strong *within*
a batch and reasonable *across* batches (all batches were given the same core reference-ID list), but wasn't
exhaustively cross-checked entity-by-entity across all 63 new files. Spot-checked for degenerate/placeholder
output (none found) but not for perfect referential integrity across all 74 files combined.
