# Phase 11 — Data Requirements Catalogue

Every data element displayed, entered, derived, or passed between steps of the Mobile Postpaid Activation journey, with source and **current-build** storage classification. Classification is based on what `NewPostpaidWizard.tsx`'s `onSubmit` (lines 625-648, confirmed directly) actually writes to `mockDataEngine.create('orders', {...})` — not on what a production system *should* store; any production-classification claim beyond that is explicitly tagged [INFERRED] with reasoning, per the brief's instruction.

**Ground truth (confirmed by reading `NewPostpaidWizard.tsx:625-648` directly):** the `orders` record created on submission contains exactly: `orderId, orderType, orderSubType, status, customerName, productId, discountId, addonIds, msisdn, numberPriceQAR, simType, simSerial, billingProfileId, newBillingProfileName, billCardLast4, dueTodayQAR, monthlyRecurringQAR, createdBy, sourceChannel, attachments`. Everything else collected during the journey is **not** written to the order — it lives only in the in-memory/sessionStorage wizard draft (`workflowStore`) for the duration of the session, or (for a couple of fields) only in local React component state that doesn't survive a refresh.

## Storage classification summary (this build only — all "none/session" claims are [VERIFIED] by direct code read; no [INFERRED] production claims are made beyond what's noted below)

- **Never stored at all, anywhere, even transiently:** full card number (MPA-DATA-014), uploaded document file bytes (MPA-DATA-021, MPA-DATA-031)
- **Session-only (sessionStorage via `workflowStore`), lost on tab close, never reaches the mock backend:** the majority of collected fields — everything not explicitly listed in the `orders` `createRecord` payload above
- **Persisted to the mock `orders` collection (survives the session, but is an in-browser mock with no real backend — see `mockDataEngine.ts`):** `orderId, orderType, orderSubType, status, customerName, productId, discountId, addonIds, msisdn, numberPriceQAR, simType, simSerial, billingProfileId, newBillingProfileName, billCardLast4, dueTodayQAR, monthlyRecurringQAR, createdBy, sourceChannel, attachments`
- **Persisted to the mock `customer-activities` collection:** `activityNumber, orderId, actionTaken, notes (incl. WinCash reference), transactionDate`
- **[INFERRED] Production storage classification** (the brief explicitly permits this one inference, since the current build has no real backend to observe): a real implementation would need backend/persistent storage for every PII field currently discarded client-side (address, full name/DOB/nationality/gender, email, alt phone, signature image) to satisfy the CAF's own legal purpose (a signed application form with no retained signature is not a valid audit record) — reasoning: a legally-binding customer application form is meaningless if the signature that makes it binding is discarded, so production necessarily must persist MPA-DATA-030 somewhere the current build does not.
