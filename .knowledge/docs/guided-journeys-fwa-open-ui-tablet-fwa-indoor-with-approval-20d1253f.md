## Purpose

### Summary of the approval-specific mechanics (vs. base FWA Indoor flow)
- Trigger observed in-flow: a "Connection Details" popup warns when a customer already has 2+ postpaid connections and recommends checking credit policy / seeking credit control approval — plausibly the business condition that routes this scenario into the approval path.
- On finishing the wizard, the agent gets an explicit message that the order is **"submitted for approval"** with an order number, rather than being completed immediately, and can track it under "My Sales Order" / "My Orders for approval".
- A separate **Test Manager** login/role, with a minimal menu (Home, Order Approval only), works a **TM SR Queue View** of approval queues and an **Order Activities Queue** shared across multiple guided journeys (New FWA Tablet, New Fixed Line Tablet, New Postpaid, etc.), not just FWA.
- The manager reviews the order via four tabs — **Attachments**, **Order Details**, **Activities**, **Agents Details** — and can open each attachment (Qatari ID front/back, CAF, Supplementary Form) in a document viewer before deciding.
- Three explicit decision actions: **Approve**, **Reject - Correction**, **Reject - Drop Order**.
- Approve requires a confirmation dialog ("By clicking submit, I agree that I have verified all the documents and details to proceed with submission") plus a mandatory-feeling Comments field.
- The decision is recorded and visible in **Activities History** with an "Order Approval" column value of Approved/Rejected (rejection example seen: "ID image not clear").
- After approval, the backend order reaches Status **Complete** / Fulfillment Status **Complete**, and the FWA service line items appear as **Active** installed assets on the account, with live usage buckets — i.e., approval gates provisioning/activation.
- The CAF requires an additional **Supplementary Form** attachment (distinct from the base CAF) before Step 8 can be completed — an explicit inline validation error ("Please select Supplementary Form before continuing.") enforces this — consistent with the earlier low-confidence extraction's "Mandatory Supplementary form" caption.
- SIM/CPE serial entry is validated against UIM (inventory) in real time, surfacing several distinct backend error states: "SIM Card does not exist in UIM", "SIM Serial # must be 19 digits", "SIM Card already assigned in UIM", and a deeper service-layer error "CPE Serial Number ... is not free in UIM ... Contact the System Administrator with Reference #..." — these correspond to the "Errors from UIM Inventory: Invalid CPE" caption noted in the prior low-confidence pass.
