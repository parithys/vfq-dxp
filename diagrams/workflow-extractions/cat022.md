## Journey Overview

A postpaid mobile (or IOT/Corporate Internet) customer's connection is migrated down to
prepaid. Per the CRM Journeys catalogue, this is executed as a manual **"Action through
Vanilla (Open UI desktop)"** — i.e., an agent-driven back-office action, not a guided
wizard — available to both CBU and EBU segments. A second, distinct execution path exists
for scheduling this same migration ahead of time via **Future Dated Orders (FDO)** in
Open UI ("Post to Pre-Migration" order type), restricted to **Retail & Retention channels
via Siebel** only. Both paths enforce materially the same business rules (outstanding
balance clearance, 100 QAR fee, one-postpaid-one-prepaid cap in the immediate case), but
the FDO path additionally re-validates at a future execution date and layers in
scheduling-specific mechanics (reminder notifications, 30-day window, penalty refund on
customer cancellation).

## Workflow Steps (numbered)

1. **Trigger — customer requests downgrade to prepaid.** Handled by a retail/retention
   agent as a manual Vanilla (Open UI Desktop) action. *(Source: CRM Journeys catalogue
   row 22 — "Action through Vanilla (Open UI desktop)".)* For the scheduled variant, this
   is raised specifically from **Retail & Retention** teams via **Siebel**. *(Source: FDO
   doc, FDO Order Types table — "Post to Pre-Migration ... Mobile (Postpaid, IOT,
   Corporate Internet) ... Siebel (Retail & Retention Only)".)*
2. **Eligibility / cap check — one postpaid + one prepaid per consumer.** A consumer
   customer may hold at most two billing profiles: one postpaid and one prepaid (no cap
   stated for enterprise). *(Source: Day5 Session 2, [00:27:34].)*
3. **Calculate migration penalties manually.** Agent manually calculates any applicable
   penalties — explicitly named examples: **star number penalty, contract penalty, "etc."**
   — and places a **modify order** to charge the penalty to the customer. This is a named
   "Agent Manual Action," not a system step. *(Verbatim, FDO doc: "Calculate the penalties
   (if any like star number, contract penalty, etc.) manually and place a modify order to
   charge the penalty to the customer.")*
4. **Outstanding balance check — must be ≤ 0.** Agent must ensure the outstanding balance
   is cleared to zero; Siebel enforces a **system validation** that the outstanding amount
   is ≤ 0. If there is an outstanding bill, an **error message is displayed and the order
   will not go through.** *(Verbatim, FDO doc, Agent Manual Actions #2 and System
   Validation: "If there is outstanding bill, Error message will be displayed, and order
   won't go through.")*
5. **Execution-date constraint.** Agent must ensure the execution date is limited to the
   **first upcoming bill cycle date**, so next month's rentals are not applied to the
   customer. *(Verbatim, FDO doc, Agent Manual Actions #3.)* General FDO ceiling: **maximum
   30 days ahead** for any FDO request. *(Verbatim, FDO doc, FDO Business Rules: "The
   maximum number of days up to which an FDO can be raised will be limited to 30 days.")*
6. **Collect 100 QR/QAR migration fee before raising the request.** Agent collects the fee
   **upfront**, before the request is raised (FDO variant: explicit precondition to raising
   the request). *(Verbatim, FDO doc, Agent Manual Actions #4: "Agent to collect the 100QR
   migration fee before raising the request.")* For the immediate (non-FDO, Vanilla) path,
   the workshop describes the fee as applied on the **final bill**, with the agent
   **manually adding it by customizing the order**, subject to **manager approval** —
   flagged as **not automated today**, and a **revenue-leakage risk if forgotten**.
   *(Source: Day5 Session 2, [00:25:00], [00:28:57]/[00:29:04], [00:29:34].)*
7. **Reminder-point re-check.** Once the FDO request is placed, on the reminder SMS date
   (3 days before execution — per general FDO notification rules), **Siebel will check the
   billed/unbilled usage** for the MSISDN again. *(Verbatim, FDO doc, Agent Manual Actions
   #5.)*
8. **Execution-day re-validation.** On the day of execution, Siebel validates again that
   billed/unbilled amount is ≤ 0. **If yes → FDO is processed; if no → FDO request is
   cancelled and the customer is notified.** *(Verbatim, FDO doc, Agent Manual Actions #6.)*
9. **Billing profile / revenue-type change.** Migration converts the customer's billing
   profile and revenue type from postpaid to prepaid. *(Direct statement of the journey
   itself, CRM Journeys catalogue row 22: "To Migrate Existing Postpaid Connection to
   Prepaid.")* Note: for the reverse direction, the FDO doc explicitly states "billing
   profile has to be created through BAU order journey; FDO request journey will not
   create billing profile" — no equivalent explicit statement exists for the Post-to-Pre
   direction in the sources reviewed; modeled here as a direct consequence of successful
   migration, consistent with both sources' framing of the journey's purpose.
10. **BRM overpayment handling.** Remaining prepaid balance posts as an **overpayment in
    BRM**: the **monetary balance transfers as advance/credit**; **non-monetary voice/data
    buckets are lost** (do not transfer). *(Source: Day5 Session 2, [00:29:57], [00:31:32].)*
11. **Notifications.** SMS and billing-email notifications sent at submission, 3-day-before
    reminder, execution success/failure, modification, and cancellation (including failure
    after 3 auto-retries due to open order); English and Arabic; sender
    `noreply@vodafone.qa`; every notification logged as an agent-visible activity.
    *(Verbatim, FDO doc, general FDO Notifications section.)*
12. **Order/request reaches terminal status.** FDO statuses: **Initial** (submitted,
    awaiting execution) → **In-Progress** (picked up by system) → **Order Submitted**
    (created as order in Siebel) → **Success** (Siebel order completed) | **Failed**
    (could not be submitted for provisioning) | **Cancelled** (user-cancelled or cancelled
    due to another FDO's execution). *(Verbatim, FDO doc, "The various status of FDO.")*
13. **Customer-initiated cancellation → penalty refund.** If the customer cancels the
    migration request, **penalty refund is handled by business process** (i.e., a separate,
    named-but-unspecified business process, not further detailed in this source).
    *(Verbatim, FDO doc, Agent Manual Actions #7: "In case, the customer cancels the
    migration request then penalty refund will be by business process.")*

## Decision Points

- **D1 — Does the customer already hold an existing prepaid billing profile?**
  (one-postpaid/one-prepaid cap). Yes → ineligible, request rejected. No → proceed.
  *(Day5 Session 2, [00:27:34].)*
- **D2 — Is the outstanding balance ≤ 0 (cleared)?** Checked twice for the FDO path: once
  at request/agent-manual-check time, again on the reminder date, and again at execution.
  No → order blocked with an error message ("won't go through"); for FDO, request is
  cancelled and customer notified. Yes → proceed. *(Verbatim, FDO doc, Agent Manual
  Actions #2, #5, #6; System Validation.)*
- **D3 — Is the requested execution date within the first upcoming bill cycle / ≤30 days?**
  No → cannot be scheduled via FDO under these rules. Yes → proceed. *(Verbatim, FDO doc,
  Agent Manual Actions #3; FDO Business Rules.)*
- **D4 — Has the 100 QAR fee been collected/applied (and, in the immediate channel,
  manager-approved)?** No → cannot raise the request (FDO: fee collection is a stated
  precondition) / order incomplete (immediate channel: manual step, no system gate exists
  today — this is the revenue-leakage risk). Yes → proceed. *(FDO doc, Agent Manual Actions
  #4; Day5 Session 2, [00:28:57]/[00:29:04], [00:29:34].)*
- **D5 (execution-day, FDO) — Is billed/unbilled amount still ≤ 0 at execution?** Yes →
  FDO is processed. No → FDO request cancelled, customer notified. *(Verbatim, FDO doc,
  Agent Manual Actions #6.)*

## Exception Handling

- **Outstanding bill present:** system displays an error message and the order does not go
  through (immediate/system validation). *(Verbatim, FDO doc, System Validation.)*
- **Outstanding balance reappears at execution (FDO):** FDO request cancelled, customer
  notified. *(Verbatim, FDO doc, Agent Manual Actions #6.)*
- **General FDO execution failure** (system failure, incident, order load, or an open order
  on the MSISDN): request is cancelled, reason captured in the custom table; requests
  failed specifically due to an **open order** get **3 automatic retries**; anything still
  unresolved (including failures from system failures/incidents/order load) is
  consolidated into a **daily operations report**. Failed FDO orders must **never be
  manually cancelled** by staff. *(Verbatim, FDO doc, "Handling Failures" + FDO Business
  Rules: "Don't cancel any FDO failed order.")*
- **Customer cancels the migration request themselves:** any penalty already assessed is
  refunded, per a separate (unspecified) business process. *(Verbatim, FDO doc, Agent
  Manual Actions #7.)*
- **FDO lapses the bill cycle and customer is charged regardless:** customer must contact
  customer care/retail and raise a Trouble Ticket (TT) to pass an adjustment. *(Verbatim,
  FDO doc, "Handling Failures.")*
- **Agent forgets to apply the 100 QAR fee (immediate/Vanilla channel):** explicitly named
  in the workshop as a **revenue-leakage risk** — no system control prevents order
  completion without the fee today. *(Day5 Session 2, [00:29:34].)*
- **Non-monetary balance loss:** unused voice/data bucket value is forfeited on conversion
  — not a system error, but a customer-impacting side effect worth flagging. *(Day5
  Session 2, [00:31:32].)*
- **All modification/cancellation of the FDO request itself** is only permitted while
  status is **Initial**. *(Verbatim, FDO doc, FDO Business Rules.)*

## Business Rules

- **100 QAR/Riyal manual migration fee.** FDO channel: agent must collect it **before**
  raising the request. Immediate/Vanilla channel: agent manually adds it to the final bill
  by customizing the order, subject to manager approval; explicitly described as "not
  automated" and a revenue-leakage risk if omitted. *(FDO doc, Agent Manual Actions #4;
  Day5 Session 2, [00:25:00], [00:28:57]/[00:29:04], [00:29:34].)*
- **One-postpaid-one-prepaid cap.** Consumer customers may hold at most one postpaid + one
  prepaid billing profile simultaneously; no such cap applies to enterprise customers.
  *(Day5 Session 2, [00:27:34].)*
- **BRM overpayment handling.** Remaining prepaid monetary balance transfers into BRM as
  advance/credit; non-monetary voice/data bucket balances do not transfer and are lost.
  *(Day5 Session 2, [00:29:57], [00:31:32].)*
- **Outstanding balance must be ≤ 0** before the migration can proceed — enforced by
  Siebel system validation, re-checked at the reminder point and again at execution
  (FDO channel); an outstanding bill triggers a hard error and the order will not go
  through. *(Verbatim, FDO doc.)*
- **Manual penalty calculation and charge.** Agent manually calculates penalties (star
  number, contract penalty, etc.) and raises a **modify order** to charge them — not a
  system-automated calculation. *(Verbatim, FDO doc, Agent Manual Actions #1.)*
- **Execution window constraint.** Execution date limited to the first upcoming bill
  cycle (so next month's rental isn't charged); general FDO ceiling of 30 days ahead for
  any FDO request type. *(Verbatim, FDO doc.)*
- **Penalty refund on customer-initiated cancellation** is handled via a separate business
  process (not detailed further in this source). *(Verbatim, FDO doc, Agent Manual Actions
  #7.)*
- **Channel/segment scope (FDO channel).** Post-to-Pre Migration FDO applies to Mobile
  Postpaid/IOT/Corporate Internet, **Retail & Retention only**, via **Siebel** only (not
  MVA/Web, unlike the reverse Pre-to-Post direction which also supports MVA/Web).
  *(Verbatim, FDO doc, FDO Order Types table.)*
- **Failed FDO orders must never be manually cancelled by staff.** *(Verbatim, FDO doc,
  FDO Business Rules.)*
- **Catalogue-level scope:** available to both CBU and EBU segments; executed as a manual
  Vanilla (Open UI Desktop) action, with no guided journey (Desktop or Tablet) built for
  this direction as of the catalogue snapshot. *(CRM Journeys catalogue row 22.)*

## Data Inputs / Outputs

**Inputs:**
- Postpaid MSISDN / account identifier (existing postpaid, IOT, or Corporate Internet
  connection)
- Current billing profile state (for the one-postpaid/one-prepaid cap check)
- Outstanding billed/unbilled usage balance (checked at request time, reminder date, and
  execution date for FDO)
- Penalty inputs: star number status, contract terms/tenure (for manual penalty
  calculation)
- Requested execution date (must fall within first upcoming bill cycle / ≤30 days)
- 100 QAR/QR migration fee collection record
- Manager approval (immediate/Vanilla channel fee application)

**Outputs:**
- Modify order charging the calculated penalty to the customer
- Updated billing profile (postpaid → prepaid; revenue type changed)
- Final bill line item / upfront collection reflecting the 100 QAR migration fee
- BRM overpayment/advance-credit record for any transferred monetary balance
- Forfeited non-monetary balance (voice/data buckets) — no output record, simply lost
- FDO order status (Initial/In-Progress/Order Submitted/Success/Failed/Cancelled) and
  order-ID cross-stamp in the custom FDO table
- SMS/billing-email notifications (submission, reminder, execution result, modification,
  cancellation) logged as agent-visible activities
- Daily operations report entry (for unresolved FDO failures)
- Penalty refund transaction (if customer cancels, via separate business process)
