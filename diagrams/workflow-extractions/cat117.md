## Journey Overview

**Catalogue #117 — "PMN Suspension"** (Journey Category: **Manage**; Type: **Workflow/Task**)

"PMN" = Park My Number. This is the renamed/redesigned successor to the legacy "voluntary suspension" journey. In the target (to-be) design, a customer who wants to temporarily stop using a number without a full disconnection is no longer put on a distinct "suspended" status — instead the account is moved onto a specific low-cost plan (the "park my number" plan) via a **Modification Order**. The plan carries a nominal fee (35 QAR) prepaid for a four-month term, and the account's credit limit is forced to zero for that period. The journey is deliberately **not** a self-service/retail journey — it is restricted to specific (unspecified in source) authorised roles and is executed as a **back-office, ticket-driven process**, applied through the Vanilla/Open UI desktop channel, available to both CBU (consumer) and EBU (enterprise) customers, and used specifically for service types that lack PYN ("Pay-Your-Number"-type, per catalogue description) functionality.

## Workflow Steps (numbered)

Sourced strictly from the two documents above; the source gives a decision-level and governance-level description rather than a granular field-by-field script, so steps are stated at the level of granularity the evidence actually supports.

1. **Request/trigger.** A request is raised to park (temporarily suspend) a customer's number/service instead of fully disconnecting it. (Source does not specify whether the request originates from the customer via a call/retail contact or is agent-initiated; only that the *execution* of the change is back-office, not retail self-service.)
2. **Ticket creation.** A back-office ticket is created to track the request. Per the governance model in the same document, "a ticket is always created ... even when a change isn't allowed" for restricted/sensitive changes, and the same ticket-driven pattern is stated to apply to manual suspension.
3. **Role/authorisation check.** Only authorised back-office roles/teams may execute the change ("restricted to specific roles"; general governance principle in the doc: "Only authorised teams (e.g., fulfilment) can execute restricted changes").
4. **Eligibility validation.** Per the general governance principle stated in the same document for restricted/sensitive changes, the system should validate eligibility "before or during ticket creation to avoid invalid requests." The source does not spell out the specific eligibility criteria for PMN Suspension (e.g., outstanding balance checks, service type exclusions) beyond the catalogue note that it is used "for Specific Service Types which don't [have] PYN functionality."
5. **Apply the plan change (Modification Order).** The account is switched onto the "park my number" plan via a Modification Order (per the catalogue row) rather than via a separate suspension/status flag. This is the redesign decision: "will always be implemented as a plan change" rather than a legacy suspension state.
6. **Plan/billing parameters applied.** The new plan is provisioned with: 35 QAR fee, four-month term, paid upfront; and the account's credit limit is set to zero for the duration.
7. **Outcome.** The number/service is effectively parked — usable state constrained by the zero credit limit and the low-rental plan — without a full disconnection.

No further downstream steps (e.g., automatic reversal at end of four months, renewal process, or reconnection/un-park procedure) are described in the source material.

## Exception Handling

- **Not authorised / role check fails:** the requested change is not executed. (Exact rejection messaging, notification, or SLA is not in source.)
- **Invalid/ineligible request:** per the general governance principle in the document (stated for the bill-cycle-change example, and asserted to be the same ticket-driven pattern applied to manual suspension), a ticket is still created even when the change isn't allowed, and is "auto-resolved in real time" — i.e., the ticket exists as a record but resolves immediately without further action, rather than sitting in a queue.
- No other exception paths (e.g., customer disputes, mid-term cancellation of the parked plan, non-payment of the 35 QAR fee, service types where PYN functionality already exists and PMN is therefore not applicable) are described in the source. The catalogue description implies an eligibility boundary ("Specific Service Types which don't [have] PYN functionality") but does not describe what happens for services that fall outside that boundary — flagged as unknown.

## Business Rules

Directly cited from source, verbatim facts:

1. **Plan change, not suspension status.** "Voluntary suspension is being discontinued and will always be implemented as a plan change" — no more separate suspended account/service state; the mechanism is a plan swap. [workshop doc, INDEX.md decision line; Section 6 of .docx body]
2. **Renamed "manual suspension."** The journey/business-facing name changes from "voluntary suspension" / "park my number" to "manual suspension." [same source]
3. **35 QAR fee.** The replacement plan carries a 35 Qatari Riyal charge. [same source] (Note: INDEX.md line literally says "35 Rial" — Qatar's currency is the Qatari Riyal, abbreviated QAR; this is the same figure, restated in the standard currency code per the task brief's "35 QAR.")
4. **Four-month term, paid upfront.** The plan/fee is upfront-paid and covers a four-month period. [same source]
5. **Credit limit set to zero.** For the duration of the parked plan, the account's credit limit is forced to zero. [same source]
6. **Role-restricted execution.** Only specific (unnamed) roles may execute this change. [same source]
7. **Back-office, ticket-driven — not a retail journey.** The process runs through back-office ticketing rather than a customer-facing/retail self-service journey. [same source]
8. **Channel: Vanilla / Open UI desktop.** Per the catalogue row, the action is performed through the "Vanilla (Open UI desktop)" interface, not the Guided Journey desktop/tablet UI (both marked "No" in the catalogue for this row).
9. **Applied via Modification Order.** Per the catalogue description, the mechanism is a "Modification Order for Specific Service Types which don't [have] PYN functionality."
10. **Available to both customer segments.** Catalogue row marks `CBU = Yes` and `EBU = Yes`, i.e., both consumer and enterprise business units can have this journey type applied.
