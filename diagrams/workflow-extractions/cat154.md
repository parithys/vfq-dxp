## Journey Overview

An authorized billing-team user opens a customer's Billing Profile (via the customer/account record in Open UI Desktop, Vanilla/manual action path — no guided wizard exists for this journey) and changes the Bill Cycle date (e.g., from the 1st to the 15th, or 15th to 1st). The system checks a **configurable eligibility business rule** before allowing the change. A support ticket is created for every bill-cycle-change attempt regardless of outcome. If the change is not allowed, the ticket is auto-resolved in real time (i.e., closed automatically, not queued for manual handling) and the change is rejected. If allowed, the Bill Cycle value on the Billing Profile is updated.

## Workflow Steps

1. **Trigger:** A request to change a customer's bill cycle date arrives (channel/origin not specified in source — could be customer-initiated via care/retail contact, or agent-initiated; source only establishes that execution is restricted to the billing team).
2. **Actor authorization gate:** Only users in the **billing team role** may perform this action (per workshop decision, source #2). The catalogue's "Action through Vanilla (Open UI desktop)" comment confirms this is a manual back-office/administrative action, not a self-service or standard retail-agent guided journey.
3. **Billing team user opens the customer's Billing Profile** in Open UI Desktop (Vanilla path) — per catalogue description: "Click on bill profile and select the Bill cycle to change from 1st to 15 or 15 to 1st."
4. **User selects the new Bill Cycle value** (the catalogue names only two concrete values in the corpus: 1st and 15th of the month — consistent with the "Bill Cycle 15" value seen on a real Billing Profile in the Modify CPE guided journey, source #3).
5. **System evaluates the eligibility business rule** (decision point — see Decision Points below). This rule is described in source #2 as **configurable, not hard-coded** — i.e., the eligibility logic is data/config-driven so it can be changed without a code release, but the exact conditions the rule evaluates are not detailed in the source.
6. **A ticket is created unconditionally** at this point — the workshop decision states a ticket is "always created even when a change isn't allowed" (source #2). This implies ticket creation happens as part of, or immediately following, the eligibility check, before/regardless of the accept/reject outcome.
7a. **If eligible:** the bill cycle change is applied to the Billing Profile; the associated ticket is presumably resolved as part of successful completion (source does not explicitly describe the "allowed" path's ticket disposition — only the rejection path's auto-resolution is described).
7b. **If not eligible:** the change is rejected; the ticket that was created is **auto-resolved in real time** (source #2) rather than left open for manual handling.

**Unknown / not in source:** the precise UI steps between "select new Bill Cycle value" and "system evaluates eligibility" (e.g., is there a confirmation screen, does the agent see the rule's pass/fail reason, is there an order object created similar to the Modify CPE journey's Sales Order pattern). No Guided Journey screenshots exist for catalogue #154, so these mechanics cannot be confirmed from the corpus.

## Decision Points

- **Eligibility check:** "Is this bill cycle change allowed per the configurable business rule?"

## Business Rules

1. **Role restriction:** Bill cycle changes are restricted to specific roles — named as "billing team" (source #2). This is the only role explicitly named as authorized; the source does not list any other roles that may or may not perform this action, aside from the open question below.
2. **Configurable eligibility rule:** the business rule that determines whether a given bill-cycle-change request is eligible must be configurable (business/config-owned), not hard-coded into the application (source #2). The rule's actual conditions are not specified in the source.
3. **Mandatory ticket creation:** a ticket is always created for a bill-cycle-change request, independent of whether the request is ultimately allowed (source #2).
4. **Auto-resolution on rejection:** when a change is not allowed, the ticket created for it is auto-resolved in real time (i.e., no manual ticket-handling queue for the rejected case) (source #2).
5. **(Supporting/contextual rule, not specific to #154):** a billing account holds exactly one bill profile, and multiple services can link to one billing account (source #2, same workshop session) — relevant context for what a "bill cycle change" actually modifies (the Bill Cycle attribute of the customer's Billing Profile record).
