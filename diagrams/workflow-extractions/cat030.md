## Journey Overview

An adjustment (monetary or non-monetary credit/debit applied to a customer's billing item or bucket) is requested through one of **two distinct, non-converging paths** depending on whether it is an **individual** (single-account) adjustment or a **bulk** (multi-account/multi-service) adjustment:

1. **Individual adjustment path** — ticket-based, routed through a delegation-of-authority (DOA) approval hierarchy inside the ticketing/CRM tooling.
2. **Bulk adjustment path** — request logged in an offline **PowerApps portal**, approved offline outside the system, then the approved data is manually pulled into an Excel file and posted to BRM (Billing and Revenue Management) by a billing-ops user.

The transcript is explicit that these are "two adjustment paths" (00:23:52) with different mechanics, different actors, and — critically — the bulk path's approval step happens **outside** any system of record ("approval done offline," 00:26:34; "Bulk adjustment approval is done offline," business rule at 00:27:25). The target/future design (00:26:34) proposes moving bulk posting into a DXP-integrated portal, but approval itself would still be offline per the transcript as discussed in this session.

## Workflow Steps (numbered)

### Path A — Individual adjustment (ticket + DOA)
1. A requester (a Billing/Care agent, per the account-level adjustment context in this workshop) identifies an adjustment need on a customer account/service and raises a **ticket** requesting the adjustment (00:23:38).
2. The ticket/request is created with **created-by details** captured (00:23:38) — i.e., who requested it is recorded on the ticket.
3. The request does **not** route to billing operations directly; instead it is routed into the **DOA (delegation of authority) hierarchy** for approval (00:23:38, 00:23:52).
4. An approver at the appropriate DOA level reviews and approves or rejects the request. The transcript states there is a designed DOA specifically "for adjustments" (00:23:52) and that this individual path is "routed to the CIO/system" as one of "two adjustment paths" (00:23:52) — the transcript does not further specify how many DOA tiers exist or what triggers escalation between tiers beyond this.
5. On approval, a business rule distinguishes the direction of the adjustment: an **increase** goes through the approval routing described above; a **decrease** is instead "only available with back office" (00:35:30) — i.e., decreases are not routed the same way and require back-office handling rather than (or in addition to) DOA approval. The transcript does not elaborate further on what "back office" execution entails procedurally.
6. Once approved, the adjustment is posted. Adjustments are posted at the **overall account level** and reflect across all billing profiles under that account (00:38:28), not scoped to a single billing profile.
7. A free-text comment/reason is expected to be entered against the adjustment so frontliners can see why it was posted (00:28:36, 00:35:35) — this is described in the transcript as a target/functional requirement rather than confirmed current-state behavior for the legacy screen.

### Path B — Bulk adjustment (PowerApps + offline approval)
1. A user (bulk requester) logs the bulk adjustment request in the current **PowerApps portal** (00:24:44, 00:25:33).
2. Approval for the bulk request is **taken offline** — i.e., outside the PowerApps portal / outside any system workflow (00:24:44, 00:27:25).
3. Once offline approval is obtained, the underlying Excel file is **manually pulled out** and **manually posted** / sent for posting to BRM (00:24:44, 00:25:33).
4. The transcript notes multiple reasons a bulk adjustment request can be rejected during this handling — "it is not simply uploaded and posted" (00:27:41) — but does not enumerate the specific rejection reasons.
5. Bulk adjustments, once posted, are applied to all services within the bulk and the account is associated to the relevant link/billing profile (00:22:33).
6. (Prepaid-specific sub-case) For prepaid recharges spanning multiple bucket IDs, the current process requires the agent to create a **separate adjustment per bucket ID**, one at a time (00:29:36) — a manual, repetitive step the workshop flags as a pain point.

### Target/future-state bulk path (discussed as a design intent, not yet built)
7. A billing-ops user with DXP access would select an **offline-generated file** containing account number, billing profile, ledger/bucket ID, and description (00:26:34, 00:26:48).
8. The user uploads and posts that file to BRM directly from DXP, with the approval itself still performed offline (00:26:34).
9. The user can see the **status** of the bulk request in DXP, including failures and rejection reasons for any rows, so failed rows can be corrected and re-uploaded (00:27:34, 00:28:15).
10. A single request could cover multiple buckets in one submission (both monetary and non-monetary types together), removing the current one-bucket-at-a-time limitation (00:33:41, 00:29:36/00:32:22).

## Decision Points

1. **Individual vs. Bulk** (implicit routing decision, not a system-enforced gate per the transcript): is this a single-account/service adjustment or a multi-account/multi-service bulk adjustment? This determines which of the two paths (ticket+DOA vs. PowerApps+offline) is used. The transcript does not describe a system control that enforces this split — it is a process/organizational split ("individual adjustments go through ticketing; bulk adjustments go through the bulk request portal," 00:24:33).
2. **DOA approval (individual path):** Approve or reject the ticketed adjustment request at the appropriate delegation-of-authority level (00:23:52). **Unknown/not stated:** the transcript does not name specific DOA levels, monetary thresholds, or named approver roles/titles — only that "a DOA designed for adjustments" exists and that individual requests are "routed to the CIO/system" (00:23:52). This should be flagged as a real gap; do not infer specific approval-limit figures.
3. **Increase vs. Decrease** (business-rule-driven branch, not confirmed as a system gate): an adjustment that increases a balance/charge "goes for approval," while a decrease "is only available with back office" (00:35:30). The transcript does not clarify whether "back office" involvement is itself an approval step, a different execution channel, or both.
4. **Bulk approval (offline):** Approve or reject the bulk adjustment request. This decision happens entirely outside the system ("approval done offline," 00:26:34; "Bulk adjustment approval is done offline," 00:27:25) — there is no system-recorded approve/reject event for this step in the current state described.
5. **Bulk file validation/posting:** whether each row in the bulk file posts successfully to BRM or fails, with failure reports enabling re-upload of only the failed rows (00:28:15, 00:27:41 — "multiple reasons why a bulk adjustment request can be rejected," unspecified).

## Exception Handling

- **Bulk row-level failures:** rows in a bulk adjustment file can fail to post; the target design calls for a failure report so failed rows can be corrected and re-uploaded rather than resubmitting the whole batch (00:28:15). The current-state process does not have this — failures are handled manually.
- **Prepaid multi-bucket adjustments:** current-state exception/workaround — because the screen doesn't support multi-bucket submission, agents must manually repeat the adjustment once per bucket ID (00:29:36). Flagged as a pain point, targeted for consolidation into a single multi-bucket submission (00:33:41).
- **Adjustment reason loss after 6 months:** not an in-flight exception during approval, but a downstream data-integrity issue — see Business Rules below. Frontliners cannot see why a historical adjustment was posted once the reason is purged (00:36:28, cross-referenced at line ~1170 of the raw transcript: "Frontliners cannot see why an adjustment was posted").
- **Non-monetary / prepaid adjustments bypass CRM:** "Not all adjustments are directed to CRM - non-monetary and prepaid adjustments are not" (00:42:00). This means the source-of-truth question (Siebel vs. BRM) is explicitly called out as **unresolved** in the transcript ("source of truth between Siebel and BRM must be decided as part of the solution," 00:41:53) — flagged here as an open decision, not a settled exception path.
- **No specific rejection-reason taxonomy** is given for either path (individual DOA rejection or bulk rejection) — the transcript only asserts that rejections happen and are multi-causal (00:27:41) without listing the causes.

## Data Inputs / Outputs

**Individual path**
- **Input:** ticket/request with created-by details, target account/service, adjustment amount, adjustment direction (increase/decrease), free-text reason/comment (target requirement, 00:28:36).
- **Output:** DOA approval/rejection decision; on approval, a posted adjustment reflected at account level across all billing profiles (00:38:28); adjustment reason visible for 6 months only, then purged per BRM 6+1 policy (00:35:35, 00:37:08).

**Bulk path**
- **Input:** offline-generated file with fields — account number, billing profile (identifier, not name — per requirement at 00:28:01), ledger/bucket ID, description/unit of measurement (00:26:48, 00:33:02); offline approval record (not system-captured).
- **Output:** posted adjustments in BRM applied across all services in the bulk (00:22:33); request status incl. failure report for any rows that fail to post, to support re-upload of just those rows (00:27:34, 00:28:15) — this status/failure-report capability is explicitly a **target-state** requirement, not confirmed current-state behavior.
