## Journey Overview

An existing Prepaid mobile customer is converted to a Postpaid plan through Vodafone Qatar's Open UI Desktop CRM guided process. An agent locates the customer's account/asset, launches the "Prepaid to Postpaid" guided process, confirms the customer's identity/contact details, manually searches for and selects a target postpaid promotion, reviews the plan's Bill/Smart Limit and Credit Limit, and generates a bilingual Customer Application Form (CAF) that is auto-populated from the wizard selections. The customer signs the CAF electronically. On completion, the system creates a Sales Order (Order Type: **Plan Change**, Order Sub Type: **Pre2Post**) in **Pending** status — the prepaid asset is still active at this point; conversion completes via subsequent order fulfillment, not an instant swap (source: `...-2e309556`, image12).

A parallel **Autobase** variant exists where a pre-computed migration offer (sourced from the Unica campaign engine) is already attached to the customer's asset; the agent simply Accepts it via a 3-step wizard (Contact → Offer Summary → Activity) instead of manually searching for a plan, and a backend Bulk Processing job completes the conversion end-to-end to "Complete" status automatically (source: `...-auto-7cb45c57`).

## Workflow Steps (Manual / Primary Path — Open UI Desktop)

1. **Locate customer account and asset.** Agent opens the customer's Account Summary in Open UI Desktop and confirms an active Prepaid asset exists (e.g., "Prepaid Red Promotion," MSISDN). Source: `...-2e309556`, image1.
2. **Launch guided process.** From the CRM Home menu (app-icon grid), agent enters "Guided Process" and, at the "1. Choose process" screen, selects **Prepaid to Postpaid** (offered alongside Consumer Postpaid, New Fixed Line, New Prepaid). Source: `...-2e309556`, images 2–3.
3. **Step 1 — Contact: enter/search prepaid number.** Wizard prompts "Please enter number"; field pre-filled with the prepaid MSISDN. Agent clicks "Go." Source: `...-2e309556`, image4.
4. **Step 1 — Contact: confirm identity.** System auto-populates ID Type, ID#, ID expiry, Nationality, Gender, Name, Birth date from the Qatari ID record; a "Connection Details" popup shows counts of existing Prepaid vs. Postpaid connections. Agent confirms remaining fields (Email, Language, Alt. phone #) and clicks Continue. Source: `...-2e309556`, images 5–6; corroborated by Tablet doc `...-176db740`, images 7–10 (Tablet additionally requires Qatari ID front/back document upload at this step).
5. **Step 2 — Plan: manual promotion search.** Agent types a free-text keyword (e.g., "red") into a search box filtering a grid of postpaid promotion tiles, then clicks "Apply +" on the desired plan (e.g., "Postpaid Red 350 Promotion"). This step is entirely manual — no automatic/base-driven pre-selection. Source: `...-2e309556`, image7.
6. **Step 2 — Plan: review plan detail / limits.** A confirmation modal shows Smart Limit / Bill Limit (with a note that the default must be communicated to the customer), Credit Limit, and the bundled components of the plan. Agent clicks Continue. Source: `...-2e309556`, image8; Tablet variant additionally allows editing the Credit Limit inline (e.g., down from 1000 to 50) via an "Edit Credit Limit" dropdown, source `...-176db740`, images 12–14.
7. **(Tablet-only) Step 3 — Addon & Discount.** Agent reviews/selects U Plan benefit options, paid add-ons, and discounts (may be empty if none apply). Not present as a separate step in the Desktop wizard (folded into CAF generation there). Source: `...-176db740`, image15.
8. **Step — CAF generation.** System generates a bilingual (English/Arabic) Customer Application Form, auto-populated from all prior wizard steps: Applicant details (Section 1), Billing information incl. Account credit limit and Smart/Bill Limit (Section 2), Postpaid plan/extras (Section 3), and a blank Section 4 (Superfast Broadband & Home Phone) confirming a mobile-only conversion. Source: `...-2e309556`, image9 & image11; `...-176db740`, images 16 & 18.
9. **Step — e-signature capture.** A "Please Sign" modal captures the customer's handwritten signature on a signature pad; agent/system stamps it with user + timestamp metadata. Buttons: Done / Clear Signature. Source: `...-2e309556`, image10; `...-176db740`, image17.
10. **Step — CAF finalize / Done.** Agent reviews the signed CAF (Section 3 postpaid details, disclaimer about prorated first-month billing, opt-out USSD code) and clicks Done. Source: `...-2e309556`, image11.
11. **System creates Sales Order.** A new Sales Order is created: Order Type **Plan Change**, Order Sub Type **Pre2Post**, Status **Pending**, Billing Profile Type Postpaid, MRC/NRC totals populated, Credit Limit carried over. The old Prepaid asset is still shown as active at this point. Source: `...-2e309556`, image12; `...-176db740`, image22 (tablet order, also ends in Pending).
12. **(Not captured in these documents) Agent submits order for fulfillment.** Both the Desktop and Tablet manual walkthroughs end with the order in **Pending**, awaiting Submit — neither document shows the Submit action or a post-submission Complete state for the manual path. This is an explicit gap (see below).

## Workflow Steps — Autobase Alternate Path (noted, not diagrammed as primary)

A. Agent opens the account; a pre-computed **Migration Offer** (Status "Offered," sourced from Unica campaign engine) is already attached to the Prepaid asset. Agent clicks "Go to offer migration." (`...-auto-7cb45c57`, steps 3–4)
B. Agent reviews the offer (plan name, benefits, pricing) and clicks **Accept**. (`...-auto-7cb45c57`, step 4)
C. 3-step accordion wizard: Contact (confirm identity) → Offer Summary (review Bill Limit/Credit Limit/benefits, read-only) → Activity (select Channel, add comments) → **Save and Finish**. (`...-auto-7cb45c57`, steps 5–9)
D. System submits the pre-built offer as one order ("Order request submitted successfully" confirmation) and hands off to a backend **Bulk Processing job** (job type "PreToPost"). (`...-auto-7cb45c57`, steps 11–12)
E. Bulk job asynchronously completes the conversion: creates new Postpaid Billing Profile, updates/adds/deletes line items, order status progresses from Open → **Complete**. (`...-auto-7cb45c57`, steps 13–17)

Key structural difference: the manual path ends at order **Pending** (awaiting agent Submit); the Autobase path's backend job carries the order all the way to **Complete** without further agent action.

## Decision Points

1. **Entry-path decision: Manual plan search vs. Autobase pre-computed offer.**
   - If a system-generated Migration Offer is already attached to the customer's asset (sourced from Unica) → agent takes the Autobase path (Accept offer, 3-step wizard, automatic backend completion).
   - If no such offer exists → agent takes the manual path (search/Apply a plan from the full promotion grid, 4-step wizard, order stops at Pending awaiting Submit).
   - Source: `...-2e309556` (manual, no offer present) vs. `...-auto-7cb45c57` (offer present, step 3: "Go to offer migration" link on the asset flyout).

2. **Bill Limit / Credit Limit validation at order Validate/Submit.**
   - Yes (valid): SL Limit Amount is at or above the Agent Minimum configured for the selected Bill Limit product → "Check Errors generated (0) errors," order proceeds. Source: `...-6d6b61ce`, step 10.
   - No (invalid): SL Limit Amount is below the Agent Minimum → blocking error "Bill Limit can not be set lower than Agent Minimum [N]. Please Contact the System Administrator with Reference # [ref].(SBL-EXL-00151)" — order is blocked at this state; the agent must correct the Bill Limit value and re-attempt Validate (loop back to the plan-configuration step). Source: `...-6d6b61ce`, step 13.
   - Note: this validation is documented only in the Desktop Vanilla (Siebel back-office "Upgrade Promotion") variant, not explicitly re-shown in the Open UI Desktop guided-wizard screenshots — flagged as evidence gap below for whether the guided wizard enforces the identical rule at its own Plan step.

## Exception Handling

- **Bill Limit below Agent Minimum (SBL-EXL-00151):** documented, blocking, with a specific remediation instruction embedded in the error text ("Contact the System Administrator with Reference #..."). Source: `...-6d6b61ce`, step 13. This is the only true system-rejected exception path captured across all four documents.
- **Prior abandoned Pre2Post/Post2Pre orders on the same account:** both the Vanilla doc (`...-6d6b61ce`, step 5: "two prior Pre2Post orders already Abandoned") and the Autobase doc (`...-7cb45c57`, step 1: prior abandoned "Post2Pre" order) show accounts that had failed/abandoned migration attempts before a successful run. Neither document explains why the earlier attempts were abandoned or shows the abandon action itself — this is a gap, not a fabricated detail.
- **"(HRN) Customer needs to pay advance payment of QR 100" notice (Autobase path only):** an informational/blocking-style alert shown twice (inline banner and a native browser confirm alert) during Contact confirmation, tied to this specific customer's HRN (High Risk Notification, inferred label only from the "HRN" prefix — not spelled out in source) status. It does not appear to halt the flow (agent proceeds to Continue), but its exact enforcement behavior (is payment collected before order submission, or is it advisory only) is **not documented** in the source and should not be assumed. Source: `...-7cb45c57`, steps 6–7.
- **No exception/error path is shown for the manual Open UI Desktop or Tablet wizards themselves** (e.g., what happens if the customer has no valid ID, or the plan search returns nothing) — not fabricated here because not evidenced.

## Business Rules

1. Target order classification is always **Order Type = "Plan Change"**, **Order Sub Type = "Pre2Post"** regardless of manual or Autobase path. Source: `...-2e309556` image12; `...-7cb45c57` step 13; `...-176db740` image22.
2. A postpaid Bill Limit ("Spend Limit") value cannot be set below the **Agent Minimum** configured against that Bill Limit product in Product Administration (e.g., Bill Limit Mobile = 50, Bill Limit Mobile Plus = 80); enforced at order Validate time with Siebel error SBL-EXL-00151. Source: `...-6d6b61ce`.
3. "Default Smart Limit/Bill Limit should be communicated to the customer" — a standing operational note surfaced in the plan-detail modal on both the manual and Autobase paths. Source: `...-2e309556` image8; `...-7cb45c57` step 8; `...-176db740` image12.
4. Maximum Bill Limit is capped at the account's Credit Limit — "Maximum Bill Limit is equivalent to account Credit Limit. Please communicate this to customer." surfaced as an informational alert at order Validate. Source: `...-6d6b61ce`, step 12.
5. Section 4 of the CAF (Superfast Broadband & Home Phone) is left blank whenever the conversion is mobile-line-only, confirming the CAF template is shared across mobile-only and bundled (fixed+mobile) conversions but only the relevant section is populated. Source: `...-2e309556` image11; `...-176db740` image18.
6. The prepaid asset remains **Active** at the moment the new Sales Order is created (Pending) — the swap is not instantaneous; it depends on subsequent order fulfillment (manual path) or the backend Bulk Processing job (Autobase path). Source: `...-2e309556` image12; `...-7cb45c57` steps 12–17.
7. In the Autobase path, orders are traceable end-to-end to the offer/campaign source: order Source = "UNICA", Comments = "ChannelOrderMigration", backend job Attrib04 = "UNICA", Attrib09 = "PreToPost"; the resulting Activity record is auto-tagged Area = "Migration to Postpay", Journey = "Start-up", Topic = "Automated Guided Journey" — distinguishing system-driven from manually logged activities. Source: `...-7cb45c57`, steps 12, 18–19.
8. Per `CRM_Journeys_Final_Updated_with_Type.xlsx` (Page Type row #8): this journey is flagged as available via Guided Journey on both Desktop and Tablet, plus a Desktop Vanilla (non-wizard, back-office) route; it applies to CBU (Consumer Business Unit) but not EBU (Enterprise Business Unit).
