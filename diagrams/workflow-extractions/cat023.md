## Journey Overview

**Trigger:** An existing Postpaid customer requests (via retail/care agent,
telesales, or the plan-change FDO scheduling UI) a change from their current
plan to a different plan — commercially this can be an upgrade (higher
rental), downgrade (lower rental), or PYN ("Plan Your Number" / plan-your-need,
per the catalogue naming "upgrade/downgrade/PYN").

**Actors:**
- Retail/Care Agent (Vanilla/Open UI desktop) — primary actor per the
  catalogue Comment field ("Action through Vanilla (Open UI desktop)").
- Customer — request originator; for the FDO channel variant, can self-serve
  via MVA/Web (per FDO doc, Plan Upgrade/Downgrade/PYN is available via
  Siebel, MVA, Web for Mobile Postpaid) [guided-journeys FDO doc].
- Siebel (backend order/validation engine) — executes system validations.
- Billing/BRM — pro-rata charge calculation, commitment/penalty logic
  (implied by "pro rata charges still apply" and commitment-restart
  discussion; BRM is named as the billing engine elsewhere in the corpus,
  e.g. business-workshop-day5-session-2's DOI/migration content, though not
  explicitly re-named in the plan-change section — **flagged as inferred, not
  directly stated for this specific journey**).

**Channel scope:** Desktop Vanilla (Open UI desktop) only per the catalogue
row (Tablet = No). The FDO variant additionally supports Siebel/MVA/Web for
Mobile Postpaid plan changes.

**Type note:** the system treats "upgrade" and "downgrade" as the same
underlying order type (a plan-to-plan change order); there is no distinct
order type/flag differentiating them today — the agent (or, for FDO, the
system-inferred logic) determines direction only from comparing rental values
[business-workshop-day5-session-2, 00:10:24].

## Workflow Steps (numbered)

1. **Agent/Customer initiates plan change request** for an existing Postpaid
   MSISDN, selecting the target plan (or, for FDO, additionally selecting a
   future date/time slot up to 30 days ahead) [FDO doc: "Sales/Frontliners
   Journey" — Create Modification order].
2. **System looks up the account/MSISDN and current plan/promotion** to
   establish the baseline for comparison (needed to infer upgrade vs.
   downgrade — see Business Rules).
3. **Eligibility check** — system validates the customer/MSISDN is eligible
   to move to the selected plan [FDO doc: "Eligibility to move to the
   selected plan"]. *(Decision point — see Decision Points.)*
4. **Billing profile status check** — system validates the billing profile is
   not in Collections [FDO doc: "Bill Profile should not be in Collections"].
   *(Decision point.)*
5. **Barred-state check** — system validates the MSISDN is not FMS, FNP, or
   MOI barred [FDO doc: "MSISDN should not be FMS, FNP or MOI barred"].
   *(Decision point.)*
6. **Standard BAU checks re-applied** — "all remaining BAU checks will remain
   the same such as promote active plans only etc." [FDO doc] — i.e. only
   currently-active/promotable plans/promotions can be selected as the
   target.
7. **Agent applies plan/promotion bundle** — because plans, discounts, and
   add-ons are packaged into named "promotions" specifically to prevent an
   agent from manually assembling an unauthorized discount combination
   (e.g., giving 30% when only 20% is authorized) [business-workshop-day5-
   session-2, 00:11:28, 00:12:47, 00:14:56]. Eligible add-ons/discounts for
   the new plan can be attached to the same order/request [FDO doc: "add on
   or discount eligible for the new plan can be placed in the same FDO
   request"].
8. **Agent/system infers upgrade vs. downgrade label** by comparing rental
   values of current vs. target plan/promotion (no system flag exists for
   this) [business-workshop-day5-session-2, 00:10:24].
9. **Pro-rata charge calculation** — system calculates pro-rata charges for
   the mid-cycle plan change; still applies under the FDO variant unchanged
   from BAU [FDO doc: "The pro rata charges will still be applicable with
   Plan Change FDO"]. If a manual adjustment is required, it is processed
   manually as in the existing (BAU) process [FDO doc].
10. **Order validated and submitted** to Siebel [FDO doc: generic FDO flow —
    "Validate & Submit the order"; for immediate/non-FDO changes this is the
    direct Siebel order submission].
11. **(FDO channel only) Order held in "Initial" status** awaiting scheduled
    execution date/time; customer/agent can view, edit, or cancel up to the
    "point of no return" [FDO doc: status model; "Accessibility & Control"].
12. **(FDO channel only) System picks up request for execution** on/at the
    scheduled date/time — status moves Initial → In-Progress → Order
    Submitted [FDO doc: FDO status model].
13. **Order executes**: plan change is applied to the customer account/
    MSISDN; commitment period is restarted (as-is/BAU behavior) — **flagged
    as an open regulatory risk, see Business Rules** [business-workshop-
    day4-session-2, 01:00:47].
14. **Order completes** — status Success (FDO) / order Complete (BAU),
    confirmation notification sent to customer.
15. **(FDO channel only) All other scheduled FDO requests on that account/
    MSISDN are cancelled** once the plan change executes [FDO doc: "Note:
    All FDO requests scheduled will be cancelled after plan change"].

## Decision Points

1. **Eligibility to selected plan?** — Source: FDO doc, "System Validation"
   list, item 1. If ineligible, request/order is rejected (FDO: "the request
   is cancelled, and the reason is captured in the custom table").
2. **Billing profile in Collections?** — Source: FDO doc, item 2. If in
   Collections, plan change is blocked.
3. **MSISDN barred (FMS/FNP/MOI)?** — Source: FDO doc, item 3. If barred,
   plan change is blocked.
4. **Upgrade or downgrade?** (classification only, not a hard gate) — Source:
   business-workshop-day5-session-2, 00:10:24 — inferred from rental
   comparison; does not block the transaction, but downstream commitment
   logic in principle should differ by direction per the flagged regulation
   (does not today — see Business Rules).
5. **(FDO only) Outstanding open order at execution time?** — implied by the
   general FDO failure-handling rule (3x auto-retry for requests failed due
   to open orders) [FDO doc, "FDO Notifications" / failure handling]; not
   plan-change-specific in the source text but part of the FDO execution
   engine this journey type runs through.

## Exception Handling

- **Any system validation fails (eligibility / billing-profile-in-collections
  / barred-state):** request/order is **cancelled**, and the failure reason
  is captured in the custom FDO table [FDO doc: "Plan Change Business Rules,
  item 2" and general FDO status model, "Failed" status]. Rule: **failed FDO
  orders must not be cancelled manually** [FDO doc, general Business Rules
  section].
- **Open order at execution time (FDO):** automatic 3x retry; if still
  unresolved, request is cancelled and notified to the customer, and
  unresolved failures are consolidated into a daily operations report [FDO
  doc: "FDO Notifications" section].
- **FDO lapses the bill cycle and customer is charged incorrectly:** customer
  must raise a Trouble Ticket for adjustment [FDO doc, general FDO section —
  applies across FDO order types including Plan Change].
- **Pro-rata adjustment required beyond system calculation:** processed
  manually, "as existing" (i.e., no new automation introduced for this by the
  FDO feature) [FDO doc: "Plan Change Business Rules," item 3].
- **Modification/cancellation of the plan-change request by
  customer/agent:** only permitted while FDO status = Initial [FDO doc,
  general Business Rules].

## Business Rules

- The system does **not** distinguish upgrade from downgrade as a data
  attribute; direction is inferred by the agent/system from plan/promotion
  name and relative rental value only [business-workshop-day5-session-2,
  00:10:24]. A requirement has been raised to add true upgrade/downgrade
  differentiation logic to the new (to-be) system [00:10:35].
- Plans, discounts, and add-ons are deliberately bundled into named
  "promotions" as an anti-abuse control, preventing agents from manually
  combining an unauthorized discount [business-workshop-day5-session-2,
  00:11:28, 00:12:47, 00:14:56]. A new bundling approach with business logic
  built in (rather than one promotion per plan/discount/add-on permutation)
  is called out as needed in the to-be design.
- Plan-change system validations: (1) eligibility for the selected plan, (2)
  billing profile must not be in Collections, (3) MSISDN must not be FMS,
  FNP, or MOI barred, (4) only active/promotable plans may be offered [FDO
  doc, "Plan Change – Upgrade/Downgrade — System Validation"].
- Eligible add-ons/discounts for the new plan may be bundled into the same
  order/FDO request as the plan change itself [FDO doc].
- Pro-rata charges apply on plan change; this is unchanged from the as-is
  (BAU) process even under the new FDO capability — any adjustment beyond
  system calc is manual [FDO doc].
- All other existing BAU process and validation logic is explicitly stated to
  remain unchanged under the FDO variant of this journey — "no changes" [FDO
  doc, "Plan Change Business Rules," item 4].
- All other scheduled FDO requests on the same account/MSISDN are cancelled
  once a plan change executes [FDO doc].
- Maximum 30 days ahead for any FDO request, including Plan Change FDO
  [FDO doc, general Business Rules].

### ⚠ OPEN REGULATORY RISK — Commitment-period restart on plan change (NOT RESOLVED)

Per `business-workshop-day4-session-2-postpaid-service-20260630-1-aa302f2d`
[01:00:47, 01:00:52]: **today, a plan change restarts the customer's
commitment period from month one, but the flagged regulatory position is that
on an *upgrade* the original commitment period should continue unchanged (not
restart), whereas a *downgrade* constitutes a breach of the existing
commitment and should trigger a penalty.** This was raised in the context of
the Disconnection/commitment-penalty discussion (only plan/commitment
penalties are automated today; star number and device penalties are still
checked manually). The FDO training pack does not mention this issue and its
"all existing process and validation will remain the same with no changes"
language for Plan Change FDO implies the FDO feature **carries this
non-compliant behavior forward unchanged** rather than fixing it.

This extraction does **not** attempt to resolve or adjudicate this
regulatory question — it is flagged here as an explicit open risk/gap
inherited by catalogue #23, consistent with the task instruction not to
resolve it. Anyone using this workflow to design the to-be system should treat
commitment-period handling on upgrade/downgrade as a requirement to be
re-specified, not a rule to replicate as-is.

(Related/adjacent but distinct rule, for context only, not the same issue:
star-number transfers separately restart commitment from month one regardless
of prior progress — `business-workshop-day7-session-1` [00:52:23]; star
number port-out is blocked during the commitment period as an anti-abuse
control — `business-workshop-day4-session-2` [01:05:12]. Neither of these
resolves the plan-change commitment-restart regulatory question above.)

## Data Inputs / Outputs

**Inputs:**
- Existing customer/MSISDN identifier (Postpaid account in scope; catalogue
  row title specifies "Postpaid Existing Customer").
- Current plan/promotion (system-held, looked up, not agent-entered).
- Target plan/promotion selection (agent- or customer-selected).
- Optional: eligible add-ons/discounts for the new plan.
- Optional (FDO channel only): future execution date/time slot (≤30 days
  ahead).
- Billing profile status (system-held — Collections flag).
- MSISDN barred-status flags (FMS/FNP/MOI — system-held).

**Outputs:**
- Updated plan/promotion on the customer account/MSISDN (post-execution).
- Pro-rata charge line item on the account/next bill.
- Order record in Siebel (status: Complete for immediate change; for FDO —
  Initial → In-Progress → Order Submitted → Success/Failed/Cancelled).
- Confirmation notification to customer (SMS + billing email, EN/AR) on
  submission, and (FDO) on 3-day-reminder, execution success/failure,
  modification, cancellation [FDO doc].
- FDO custom table entry cross-stamped with the order ID (FDO channel only).
- Cancellation of any other pending scheduled FDO requests on the same
  account/MSISDN, as a side-effect output (FDO channel only).
- (Unresolved/open) Commitment period end-date — currently reset to a new
  start date on every plan change; this is the flagged regulatory risk above,
  not a designed/confirmed output.
