## Journey Overview

- **What it is:** MOI Validation is not a standalone customer-facing journey but a **shared backend Task/Workflow** (catalogue Type = "Workflow/Task", Journey Category = "Support") invoked from inside other activation and migration journeys. The catalogue description is explicit: "Clicking on Tab to do MOI Validation for the ID and Backend check predefined on activation & migration journeys."
- **Trigger/start condition:** An agent working an activation or migration order reaches the identity-verification point of that order and either (a) clicks a dedicated **"MOI Validation"** button on the order toolbar (confirmed present in the Desktop Vanilla FWA CPE-modify order screen, Source #1), or (b) the system auto-fires MOI lookup after the agent keys/re-scans an ID number, as literally shown in the Passport-to-QID tablet journey ("Once 'Update ID' is clicked, all customer details are fetched based on MOI Validation," Source #6).
- **Actors:** CSR/Care Agent or Retail Sales Agent (initiates the scan/click); the backend MOI system (Ministry of Interior ID registry — acronym not expanded in any source document, MOI = Ministry of Interior per common Qatar-government usage, but this expansion itself is not stated in the corpus and should be treated as inferred, not sourced); CBS (Vodafone's existing customer/billing system, used for a cross-check in the SIM Swap variant); Tarasol (named fallback system if the MOI API does not respond, per Source #3); a Manager/back-office role for the QID-number-only override path (Source #2).
- **Duration:** Not stated in any source. No document gives a timing/SLA figure for the MOI Validation task itself.
- **Reused by (per catalogue Relationship sheet):** New Fixed line (#5), New FWA (#6), New Postpaid (#7), New Prepaid (#9), MNP Prepaid (#10), MNP Postpaid (#11), New IOT Tablet (#12) — all High-strength reuse — and Passport to QID (#26) at Medium strength. The sources consistently describe it as gating identity-sensitive order types (new activations, number ports, ID-document changes, SIM swaps) rather than being itself a single linear customer journey.

## Workflow Steps (main flow, as directly evidenced)

The corpus does not contain one single canonical screen-by-screen walkthrough titled "MOI Validation" end-to-end; it must be reconstructed from the button's placement (Source #1), the OCR->MOI chain description (Source #2/#3), and the one concrete trigger example (Source #6). The steps below are only what is directly stated across those sources — no invented sub-steps.

1. **Agent captures/re-scans the ID document.** Per Source #2, agents cannot manually type ID details in normal flow — they scan/re-scan the physical ID (QID or Passport). OCR extracts the ID number and data from the document image.
2. **OCR output is matched against the ID's barcode.** Per Source #2's stated chain: "OCR of ID → match barcode" — a first-pass internal consistency check between the OCR-read text and the document's barcode data before any external call is made.
3. **MOI API is called with the ID number.** Per Source #2 ("→ MOI API (name, DOB, nationality)") and Source #3 ("MOI API is the primary ID-data source"), the system calls the MOI backend, which returns the government's on-file name (all name fields, up to ~5-6, not truncated), date of birth, and nationality for that ID number.
4. **Secondary-parameter cross-check.** Per Source #3: MOI-returned data only takes precedence over the OCR-captured data "after a secondary-parameter cross-check (e.g., DOB, nationality, expiry) passes" — i.e., the OCR-read secondary fields and the MOI-returned secondary fields must agree before the system trusts/writes the MOI version into the contact record.
5. **(Journey-dependent extra step) CBS cross-check.** Source #2 states SIM Swap adds a third validation layer beyond OCR+MOI: matching the validated identity against the existing CBS customer/account record. The source explicitly frames this as an *addition* specific to SIM Swap ("SIM Swap has this extra third validation step"), implying it is not part of the baseline MOI Validation task itself but is layered on top by journeys that need to confirm the presenter is the existing account holder.
6. **Customer/contact record is populated or refreshed.** Concretely evidenced by Source #6: once the ID number is entered/updated and MOI Validation completes, "all customer details are fetched" into the journey (name, DOB, nationality, etc.), auto-populating downstream form fields.
7. **Order/journey proceeds (or the MOI Validation action remains available/disabled on the order toolbar).** Source #1 shows MOI Validation as one of several order-level toolbar actions (Revise, Validate, Select Favorites, Drop Order, Submit, MOI Validation, Generate Activity Plans, Cancel Order) sitting alongside the order's lifecycle — present but disabled for an order type (CPE attribute modification) that does not require identity re-validation, implying the button/task is conditionally enabled based on order type/journey.

## Decision Points

1. **Does OCR/barcode/MOI data pass the secondary cross-check (DOB, nationality, expiry agree)?**
   - **Yes →** MOI-sourced data is accepted as authoritative and written to the contact/order record; journey proceeds (Source #3).
   - **No →** Not explicitly detailed in any source what the system does on failure (no error message or reject terminal is documented for this specific cross-check failure). The only adjacent, explicitly-sourced failure/override path is the manager-level bypass below. This is a **gap**: the corpus does not state whether a failed cross-check hard-blocks the order, requires re-scan, or routes to a manual/back-office queue.

2. **Is a manager-level override needed (e.g., OCR/scan cannot resolve, or QID number needs correction)?**
   - Per Source #2: "agents cannot manually enter ID details, only re-scan; a manager-level bypass allows editing QID number only, with remaining fields validated against MOI." This implies a decision point: if re-scan repeatedly fails, an agent can escalate to a manager who may manually key the **QID number only** — but every other field (name, DOB, nationality, etc.) still goes through MOI validation, it is not a full bypass.
   - **Yes (manager override invoked) →** Manager edits QID number field only; remaining fields still validated against MOI; journey continues.
   - **No (standard flow, no override needed) →** Standard OCR/barcode/MOI/cross-check flow continues as in steps 1-4 above.

3. **(SIM Swap-specific, not confirmed as part of baseline #71) Does the CBS cross-check confirm the presenter matches the existing account holder?**
   - Not detailed with explicit Yes/No system behavior in the sources beyond the fact that this step exists for SIM Swap. No pass/fail branching text is given. Documented as a **gap**.

## Exception Handling

- **OCR misread of ID number:** Source #3 explicitly flags the risk that OCR can misread a digit (e.g., "0" read as "8"), pulling the wrong MOI customer record — and warns that a misread number could coincidentally still match a valid expiry date, defeating the two-factor (ID number + expiry) check. No corrective workflow step is described beyond this being a named risk; it is not resolved by any documented step.
- **Damaged/scratched ID cards causing OCR failure:** Named in Source #3 as a cause of scan failure; the manager-level QID-number-only override (Source #2) is the only documented remediation path.
- **MOI API non-responsive:** Source #3 states Tarasol (manual fallback) is used "only if MOI API doesn't respond" — i.e., system degrades to a manual/alternate data source rather than blocking the journey outright. No further detail on what "manual" entails operationally.
- **Identity theft with a genuine ID (fraud):** Source #2 names this as "the number one fraud reason for service operations and activations" — a case where OCR, barcode, and MOI checks all pass because the ID document itself is authentic, it just doesn't belong to the person presenting it. No technical control is described in the sources as catching this; it is stated as an acknowledged residual risk, not a solved exception path.
- **MOI database sync lag (age/minor check):** Source #4 notes a "5-8 day MOI database sync lag risk" for someone who just turned 18 — meaning an age-gating validation sourced from MOI could be briefly stale around a birthday boundary. No compensating control described.
- **CBS cross-check failing to find/match an existing account (SIM Swap variant only):** Not detailed in the sources; flagged as a gap above.

## Business Rules

(Only rules directly stated in the sources; all are either global platform rules that constrain what MOI Validation must enforce, or field-level rules from the contact-validation catalogue that MOI Validation output must satisfy.)

- MOI API is the **primary** ID-data source; Tarasol/manual entry is fallback-only, invoked solely when the MOI API does not respond (Source #3).
- All name fields MOI returns (reported as up to ~5-6 name components) must be stored in full and printed on the customer's bill — must not be truncated to a simple first/last name pair (Source #3).
- MOI-returned data overrides OCR-captured data, but **only after** a secondary-parameter cross-check (DOB, nationality, expiry) passes (Source #3).
- Agents cannot manually key ID details under normal process — ID must be (re-)scanned; only a manager-level role may manually edit the QID **number** field, with every other field still validated against MOI (Source #2).
- QID is mandatory for postpaid sales (one unspecified exception referenced but not detailed) — expats on passport are generally restricted to prepaid, capped at 5 numbers (Source #3, contextual platform rule this task must support at intake).
- ID Expiration Date must be in the future (contact-record validation, Source #5).
- Date of Birth must match the DOB embedded in the Qatari ID number itself — a stated cross-field rule ("Date of Birth and Qatari ID do not match") (Source #5).
- QID must be exactly 11 numeric digits; Passport 4-20 alphanumeric characters; GCC ID 8-20 numeric characters (format rules, Source #5).
- Contacts flagged if under 18 (age rule, Source #5); age/minor validation elsewhere is stated to be sourced from MOI/date-of-birth (Source #4).
- Certain contact-type/nationality combinations are authorization-gated ("not authorized to create Safwa Contact," "not authorized to create Qatari Contact") (Source #5) — exact relationship of these authorization rules to the MOI Validation task specifically is not detailed; included here because the source document itself cross-references this workbook as companion material to the "MOI Validation" journey row.
- For SIM Swap specifically (adjacent journey, not #71 itself), an additional CBS cross-check step is layered on top of the OCR/MOI chain (Source #2) — evidence that other journeys can extend the base MOI Validation task with journey-specific extra checks, but this extension is not itself part of catalogue #71's documented scope.

## Data Inputs/Outputs

| Stage | Input | Output |
|---|---|---|
| ID capture | Physical ID document (QID or Passport), presented for camera scan | OCR-extracted raw text/fields (ID number, and whatever the document image contains) |
| Barcode match | OCR-extracted ID number/text | Pass/fail internal-consistency signal (barcode vs OCR agreement) |
| MOI API call | ID number (QID or Passport number) | Government-of-record name (all name components), date of birth, nationality |
| Secondary cross-check | OCR-captured DOB/nationality/expiry vs MOI-returned DOB/nationality/expiry | Accept/trust decision for whether MOI data may overwrite OCR data |
| Contact/order record update | Validated MOI data (name, DOB, nationality) | Auto-populated customer/contact fields carried into the calling journey (e.g., Passport-to-QID form, new activation order) |
| (SIM Swap extension only) CBS cross-check | Validated identity | Match/no-match against existing account holder on file |
