## Journey Overview

FDO ("Future Dated Orders") lets an agent (Cops/Digital or sales/frontliner) schedule certain order
types to execute automatically on a customer-chosen future date/time, instead of executing immediately.
Phase 1 supports raising FDOs through Open UI; other channels are "Phase 2 / Coming Soon." The feature
is applicable to Consumer and Enterprise segments, for Prepaid (Pre-to-Post only), Postpaid, and Fixed
customers. The customer/agent can view, edit, and cancel a scheduled request up to a "point of no
return" (the point at which system processing begins — exact cutoff not further defined in source).

The high-level journey (per the pack's own "Sales/Frontliners Journey" slide) is:
**Create Modification Order → Select future date and time slot → Validate & Submit the order → FDO
Order Status Change → Confirmation Notification → Order Execution on selected date.**

Underneath that, the system carries the request through a formal status model (Initial → In-Progress →
Order Submitted → Success / Failed / Cancelled), with per-order-type system validations firing both at
submission time and again at execution time, plus manual agent checks required for several order types
(HRN fee collection, outstanding balance clearance, penalty calculation).

## Workflow Steps (numbered)

1. **Agent creates the base order** for a supported order type (e.g., Pre-to-Post Migration, Plan
   Upgrade/Downgrade/PYN, Add-on/Discount activation) in the originating channel (Siebel, MVA, Web, or
   Unica depending on order type — see Business Rules).
2. **Agent selects a future date and time slot** using the new Open UI fields (FDO date/time slot within
   the order). If a preferred date/time is not visible, no slot is available and the agent must choose a
   different slot.
3. **System validates the 30-day window.** The maximum number of days ahead an FDO can be raised is
   limited to 30 days. *(Decision point — see Decision Points.)*
4. **System runs order-type-specific validation** at submission time (e.g., MSISDN not FMS/MOI/collection
   barred/blacklisted for Pre-to-Post; plan eligibility and non-collections billing profile for Plan
   Change; add-on/discount eligibility for Add-on/Discount orders). *(Decision point.)*
5. **Order is validated & submitted.** On passing validation, the order and FDO request are cross-stamped:
   the generated order ID is written against the FDO request in a custom table, and the FDO request ID is
   stamped onto the order.
6. **FDO status = Initial.** The FDO request is submitted and awaiting pickup for execution. While status
   is Initial, the customer/agent may still view, edit, or cancel the request (this is the only status in
   which modification/cancellation is allowed, per Business Rules — Disconnection is a further exception,
   see below).
7. **Confirmation notification sent** (request-submission notification) via SMS and billing email, in
   English or Arabic, to both the MSISDN and the notification MSISDN; logged as an activity visible to
   the agent.
8. **Reminder notification sent 3 days before the scheduled execution date**, via SMS and billing email.
   For Post-to-Pre Migration specifically, this is also the point at which Siebel checks billed/unbilled
   usage for the MSISDN (see per-order-type rules).
9. **FDO status = In-Progress.** The FDO request is picked up by the system for processing (on/at the
   scheduled date/time).
10. **System re-validates at execution time** — order-type-specific checks are re-run (plan/add-on/discount
    eligibility may have changed since submission; outstanding balance is re-checked for Post-to-Pre
    Migration; open-order status is checked). *(Decision point.)*
11. **FDO status = Order Submitted.** The FDO request is created as an order and submitted into Siebel for
    provisioning.
12. **Siebel provisions the order.**
    - **FDO status = Success** — the Siebel order completes. → **Execution-successful notification** sent
      (SMS + billing email); order executes on the selected date; for Plan Change specifically, all other
      scheduled FDOs for that account are cancelled as a side effect once the plan change executes.
    - **FDO status = Failed** — the FDO request could not be submitted for provisioning in Siebel. → If
      failure is due to an existing open order for that MSISDN, the system **automatically retries up to
      3 times** (see Exception Handling). → **Execution-failed notification** sent.
    - **FDO status = Cancelled** — either the user cancelled it (only while status was Initial, except
      Disconnection which only the retention team can cancel), or it was cancelled automatically because
      another FDO order executed first (e.g., a Plan Change execution cancels other pending FDOs), or a
      validation failure at any stage triggered auto-cancellation with the reason captured in the custom
      table. → **Request-cancelled notification** sent (including the specific case of "Request Failed due
      to Open Order after 3 auto retries").
13. **Unresolved failures are consolidated into a daily operations report** — covering the exhausted-retry
    case plus failures from system failures, incidents, or order load (see Exception Handling).
14. **Post-execution exception path:** if FDO execution lapses the billing cycle and the customer is
    charged as a result, the customer must contact customer care/retail and raise a Trouble Ticket (TT) to
    pass an adjustment. This is a manual, out-of-band correction, not an automated part of the FDO flow.

## Decision Points

1. **Within 30-Day Window?** — "The maximum number of days up to which an FDO can be raised will be
   limited to 30 days." No path: the request cannot be raised as an FDO (implicitly must be re-submitted
   with a valid date, or handled as a normal BAU order — the pack does not further specify the reject UX,
   flagged as **UNKNOWN**).
2. **Order-Type Validation Passed? (submission time)** — order-type-specific checks (examples: Pre-to-Post
   MSISDN not FMS/MOI/collection-barred/blacklisted, ID not passport, no upfront payment in same order;
   Plan Change eligibility/non-collections/non-barred; Add-on/Discount eligibility/non-collections/not
   barred/credit limit). No path: request is rejected/cancelled at submission with the reason captured in
   the custom table.
3. **Order-Type Validation Passed? (execution time)** — re-validation at the scheduled execution moment
   (examples: Post-to-Pre outstanding billed/unbilled amount must be ≤ 0 or the FDO is cancelled and
   customer notified; recurring add-on already in assets fails; discount no longer eligible for current
   plan fails). No path: FDO status → Cancelled/Failed, reason captured, customer notified.
4. **Failed Due to Open Order?** — determines whether the automatic 3x retry applies. Yes path: system
   retries submission up to 3 times. No path (other failure causes — system failure, incident, order
   load): request is not auto-retried and instead rolls into the daily consolidated ops report as a failed
   item.
5. **Retries Exhausted (3x) Still Failed?** — Yes: status → Cancelled, "Request Cancelled" notification
   sent specifically citing "Failed due to Open Order after 3 auto retries," and the item is added to the
   daily ops report. No (a retry succeeds): flow continues to Order Submitted → Success.

## Exception Handling

- **Automatic retry:** FDO requests that fail specifically due to an existing open order for that MSISDN
  are automatically retried up to **3 times** by the system.
- **Retry exhaustion:** if still failed after 3 retries, the request is cancelled and the customer is
  notified via a "Request Cancel Notification" that explicitly cites the open-order/3-retry cause.
- **Other non-retryable failure causes** (explicitly listed): system failures, incidents, order load. FDOs
  failing for these reasons (plus exhausted open-order retries) are **consolidated into a daily
  operations report** sent to operations — this is a manual/operational follow-up channel, not further
  automated in the pack.
- **Do not manually cancel a failed FDO order** — stated as an explicit business rule/guardrail for
  agents ("Don't cancel any FDO failed order").
- **Billing-cycle lapse:** if FDO execution slips past the billing cycle and the customer is incorrectly
  charged, the customer must raise a TT via customer care/retail for a manual adjustment — this is
  outside the FDO system flow itself.
- **Post-to-Pre Migration penalty refund on cancellation:** if the customer cancels a Post-to-Pre
  migration request, any penalty refund is handled "by business process" (manual, outside the FDO
  system) — not further specified.
- **Plan Change side-effect cancellation:** executing a Plan Change FDO automatically cancels all other
  scheduled FDOs for that account (stated as a Note under Plan Change business rules) — this is a
  system-triggered cancellation exception, not a failure.
- **Disconnection cancellation restriction:** Disconnection FDOs cannot be cancelled via the app at all;
  only the retention team has cancellation access — an exception to the general "cancel while Initial"
  rule.

## Business Rules

**Status model (verbatim from source):**
- **Initial** – FDO request is submitted and awaiting to be picked for execution.
- **In-Progress** – FDO request is picked by system for processing.
- **Order Submitted** – FDO request is created as an order and submitted in Siebel.
- **Success** – Siebel order is completed.
- **Failed** – FDO request could not be submitted for provisioning in Siebel.
- **Cancelled** – user cancelled, or cancelled due to execution of any other FDO order.
- (Cross-cutting) If any validation fails, the request is cancelled and the reason is captured in the
  custom table.

**Core business rules:**
- Maximum 30 days ahead for any FDO request.
- Generated order ID is stamped against the FDO request in a custom table; FDO request ID is stamped
  onto the order (bidirectional cross-reference).
- If FDO execution fails due to order validations, the request is cancelled and the error is captured in
  the FDO table.
- Failed FDO orders must never be cancelled manually by an agent.
- Modification and cancellation are allowed only while status = Initial (Disconnection is a further
  exception — only retention team can cancel it, at any status).

**Supported FDO order types (explicit list):**
| Order Type | Service Type | Channels |
|---|---|---|
| Pre-to-Post Migration | Mobile (Prepaid) | Siebel, MVA, Web |
| Post-to-Pre Migration (Retail & Retention only) | Mobile (Postpaid, IOT, Corporate Internet) | Siebel |
| Plan Upgrade/Downgrade/PYN | Mobile (Postpaid) | Siebel, MVA, Web |
| Plan Upgrade/Downgrade/PYN | Fixed, Mobile (IOT, Corporate Internet) | Siebel |
| Disconnection (Retail & Retention only) | Mobile (Prepaid, Postpaid, IOT, Corporate Internet) / Fixed | Siebel |
| Add-on/Discount Activation/Deactivation/Modification | Mobile (Postpaid, IOT, Corporate Internet), Fixed | Siebel, MVA, Web, Unica |

During-FUT roadmap note (source's own phrasing): "During (FUT)" lists Post-to-Pre and Pre-to-Post as
currently live; "After FUT" lists Modifications, Disconnection, Plan Change, PYN as "Coming Soon" — the
pack's own status of what's live vs. planned, retained here verbatim rather than reinterpreted.

**NOT supported order types (explicit list):**
- New Activation (Mobile/Fixed)
- Transfer of Service (Mobile/Fixed)
- Add-on Activation/Deactivation (Mobile Prepaid)
- Transfer of Ownership (Mobile/Fixed)
- Port In (Mobile/Fixed)
- Port Out (Mobile/Fixed)
- Change MSISDN (Mobile/Fixed)
- SIM Swap (Mobile)
- Collection Suspend/Resume (Mobile Postpaid)
- OG Bar/Unbar (Mobile Postpaid)
- Home Move Orders / CPE (Swap) / STB (Swap) / IPTV (Add) / ONT Replacement (Fixed)
- Voluntary Suspend [Legacy] (Mobile Postpaid, IOT, Corporate Internet / Fixed)
- Voluntary Resume [Legacy] (Mobile Postpaid, IOT, Corporate Internet / Fixed)

**Per-order-type validation and manual-check detail:**

- *Pre-to-Post Migration* — System validation: MSISDN must not be FMS/MOI/collection-barred/blacklisted;
  request rejected if customer's ID on file is a passport; upfront payment (e.g. HRN fee) cannot be added
  within the same FDO order (fee must be posted as payment first). Agent manual checks: collect and post
  HRN fee before raising the FDO for existing postpaid HRN customers; no payment can be added as part of
  the FDO request (system-enforced); billing profile must be created via the BAU order journey (the FDO
  journey does not create a billing profile); agent may add add-ons/discounts alongside the migration in
  the same FDO request.
- *Post-to-Pre Migration* — Agent manual actions: manually calculate penalties (star number, contract
  penalty, etc.) and place a modify order to charge them; ensure outstanding is cleared to ≤ 0 (Siebel
  validates this); ensure execution date is limited to the first upcoming bill cycle so next month's
  rentals aren't applied; collect the 100 QR migration fee before raising the request. Siebel checks
  billed/unbilled usage on the 3-day reminder date, and again validates ≤ 0 on execution day — if not, FDO
  is cancelled and customer notified. If the customer cancels the migration request, penalty refund is
  handled by business process (manual). System validation: outstanding bill present → error message
  displayed, order does not proceed.
- *Plan Change (Upgrade/Downgrade)* — System validation: eligibility for the selected plan; billing
  profile not in Collections; MSISDN not FMS/FNP/MOI barred; all remaining BAU checks unchanged (e.g.
  promote active plans only). Business rules: add-on/discount eligible for the new plan can ride in the
  same FDO request; validation failure → cancelled with reason captured; pro-rata charges still apply
  (manual adjustment process if needed); all existing process/validation otherwise unchanged. **Note: all
  scheduled FDOs are cancelled after a plan change executes.**
- *Disconnection* — Can only be raised from Siebel, not MVA; all existing process/validation unchanged.
  Agent manual actions: manually calculate and charge penalties; ensure outstanding ≤ 0 (Siebel-validated);
  execution date limited to first upcoming bill cycle. Order cancellation: cannot be cancelled via the
  app — only the retention team can cancel Disconnection requests.
- *Add-On (Add/Remove/Modify)* — System validation: add-on eligible for current plan; billing profile not
  in Collections; MSISDN not FMS/MOI barred; credit limit not breached. Rules: multiple add-ons can be
  selected in one FDO request; recurring add-ons cannot be added twice — fails validation if the product
  is already in the assets (example given: customer requests international 50 QAR add-on for 31 July but
  already self-added it on 28 July via MVA — fails at execution); one-off/non-recurring add-ons can be
  added multiple times and will go through (example: VF Passport requested for 17 July, customer also adds
  it via MVA on 16 July — still goes through); if a plan-change FDO is also pending, the add-on eligibility
  list used at execution is for the new (post-change) plan — if eligible under the new plan it executes,
  otherwise the add-on request is rejected (example given with U Plan → Extra Plan and an International
  add-on only eligible under U Plan).
- *Discount (Add/Remove/Modify)* — System validation: discount eligible for current plan; billing profile
  not in Collections; MSISDN not FMS/FNP/MOI barred. Business rules: multiple discounts cannot be selected
  in one order (existing BAU rule); if the discount is no longer eligible at execution time, the request
  fails and is marked Cancelled.

**Notifications (cross-cutting rule):**
- Sent to both the MSISDN and the notification MSISDN.
- Delivered via SMS and billing email for: request submission, 3-day-before reminder, execution success,
  execution failure, request modified, request cancelled (including the specific "failed due to open
  order after 3 retries" case).
- Available in English and Arabic.
- Every notification Siebel sends is also logged against the FDO request as an activity, visible to the
  agent.
- Sender email address: `noreply@vodafone.qa`.

## Data Inputs/Outputs

| Input | Output | Meaning |
|---|---|---|
| Base modification order (order type, customer/MSISDN, order details) | Order created in originating system (Siebel/MVA/Web/Unica) | Agent originates the change to be scheduled |

| Order-type-specific customer/account state (MSISDN barring status, ID type, billing profile status, outstanding balance, plan eligibility, add-on/discount eligibility, credit limit) | Pass/fail validation result + captured rejection reason (on failure) | Gate that determines whether the FDO can proceed at submission and again at execution |

| Failed-due-to-open-order signal | Up to 3 automatic retry attempts; final Cancelled status + notification if exhausted | Recoverable-failure handling without agent intervention |
| Unresolved failures (post-retry, system failure, incident, order load) | Daily consolidated operations report | Operational visibility into FDOs needing manual follow-up |
| Billing-cycle lapse + erroneous charge | Customer-raised TT (Trouble Ticket) for adjustment | Manual, out-of-band billing correction path |
